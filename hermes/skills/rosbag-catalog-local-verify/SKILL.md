# rosbag-catalog 本地改动验证

## When to Use

在 rosbag-catalog 仓库做代码/模板改动后需要本地验证时：跑 pytest 前、重建本地 Compose 栈实测页面/API 前、写 HANDOFF 与同步 TODO 前。本 Skill 只覆盖本地验证；处理机部署授权与命令见仓库 AGENTS.md 和 `rosbag-catalog-status-check`/`rosbag-catalog-supervisor` 技能。

仓库 AGENTS.md 拥有工作流基线（TODO 追踪、HANDOFF、质量门禁、部署授权、提交推送）。本 Skill 只记录 AGENTS.md 未写明、但每次本地验证都会踩的坑。工作目录 `/home/wang/work/rosbag-catalog`。

## 跑测试
- **大 commit（±2000 行级）的 ocr 多轮 amend 收敛，每轮都会再抓出"上一轮修复引入/遗漏"的新 bug**（本会话四轮：第一轮抓主缺陷，第二/三轮抓修复残留——如幂等 scope 终身化、异常分类过宽），不是收敛失败而是预期形态：每轮把 findings 全修 + 补回归 + amend 后再送审，终止判据是某轮 0 findings 或仅误报；期间 Qwen 共享队列单轮 30min 级，`review_round_failed` 单请求超时按既有规则声明覆盖度。
- 一律用仓库 venv 解释器：`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv/bin/python -m pytest ...`。环境默认 python（Hermes venv）没有 pytest，直接 `python3 -m pytest` 会以 `No module named pytest` 失败。ruff 同理不在系统 PATH：用 `.venv/bin/ruff`（裸 `ruff` 报 command not found）。
- 全量 `pytest -q` 在**收集期**因某个你没改的测试文件 ImportError 中断时：多半是并行会话的未提交 WIP（`git status` 能看到该文件的改动/新增）。确认文件不属于本任务后用 `--ignore=tests/该文件.py` 重跑全量，并在 HANDOFF/汇报里如实写"排除了 <文件>（他人 WIP 导入错误）"；不要替他人修或删 WIP，也不要把该错误当成本次改动引入。
- `tests/test_web.py` 多数用例有文件级顺序依赖：表结构由 app lifespan 在首个 `TestClient(app)` 上下文创建（由文件第一个测试 `test_pages_render` 触发）。单跑依赖 DB 的用例会以 `sqlite3.OperationalError: no such table` 失败——判断回归与否：看它是否自建夹具（见下条）。**断言全局表状态（分页页数、总行数）的用例必须自洽**：独立临时 SQLite（`create_engine(tmp_url)` + `Base.metadata.create_all` + `monkeypatch.setattr(app.database, "engine"/"SessionLocal", ...)`），不依赖共享库恰好为空——否则前序测试残留行把 total 撑大，断言在单跑/全量下行为不一致（分页用例曾因此顺序污染全仓 1 failed，改自洽夹具后全仓全绿）。
- **解析外部二进制/协议格式（CDR/rosbag2 sqlite/自定义 wire）时，自洽 encode/decode 往返不算有效证据**：编码器与解码器共享同一套假设（如都漏 4 字节 ROS2 封装头、都按 offset 0 起读字段），往返恒绿但读真实数据整体错位——用户要求必须用真实样本核对。配方：ssh 到测试盘真实采集 bag，取消息行前 N 字节 hexdump 成 golden 常量写入测试（不经过仓库自己的 encoder），decoder 单测独立断言真实字节上的字段对齐 + 一个按真实格式（含封装头、真实 msg type）构造 bag 的端到端用例；msg type 以真实 bag topics 表为准（如真实前相机是 sensor_msgs/msg/Image 而非 CompressedImage），topic 匹配/解码分支按真实类型放宽并覆盖。**同类契约漂移不止字节布局：对外部生产者（decoder 子进程/第三方工具）按"产物数==输入消息数"这类 1:1 计数断言做契约时，粒度假设（每消息一产物 vs 每帧/每 scan 一产物）同样要用真实样本核对**——真实产物数与输入消息数不一致（如 44 产物 vs 1184 消息，生产者按每 scan 出一帧）时该断言让一切真实有效输入必判失败，而合成 fixture 按假设构造恒绿。真实核对必须同时计数两侧（输入消息数、产物数、产物命名与源键的对应规律），映射锚定到源数据的稳定整数键（如消息 storage_ns/message_id）而非文件名近似；产物命名不可控时用真实命名规律（如按源时间命名）在测试里复现同样的顺序保证。
- **`select(A, B, A.some_rel)` 多实体 select 不要把 relationship 列（尤其 secondary 关联表）带进投影**：关联表进 FROM 形成笛卡尔积（SAWarning、行数成倍放大、limit+1 分页判定错位）——先查主实体页，再 `rel_table.c.<fk>.in_(page_ids)` 一次批量查关联行按 id 填摘要。
- **给"限额/上限拒绝"守卫写测试前，先确认守卫实际生效在哪一层可达**：上游契约类型构造器先强制的限额（如 SceneManifest 构造即拒 >100 区间）让服务层同值守卫永远走不到——测试打真实执行点（101 构造层拒绝 / 100 端到端接受），不要为不可达的冗余守卫伪造执行路径。
- **monkeypatch settings 要 patch 到每个 import 方模块**：`app/web/*.py` 页面与 `app/services/*` 服务各自 `from app.config import settings`，只 patch service 模块的 `settings` 会让模板/页面仍读到 flag 关闭的原对象——测试静默表现为"UI 不出现"而非报错。patch 用 `dataclasses.replace(settings, **cfg)` 生成新对象后，对每个受影响模块 `monkeypatch.setattr(<module>, "settings", patched)` 各打一遍。
- **只在特定文件组合出现的失败（A 接 B 失败、B 单跑与全量都过）先怀疑测试 DB 数据污染，不是代码回归**：ad-hoc 调试进程（`.venv/bin/python -c`/execute_code）若连的是同一 sqlite，会留下永久行；多出的 bag 行把 demo 行挤出 `/bags` 第一页，表现为一批 `404`/"uid not in page" 失败。定位：`SELECT name FROM bag_record` 枚举实际行、清掉调试残留后按两个顺序重跑都须绿。测试文件自建的数据要在 autouse fixture 的 teardown 里按自有命名前缀清净（含关联的账本行），不能只靠"用完即弃"；DB fixture 必须 session-scoped 且 finally 无条件 rollback+close——测试中途异常时未关闭的 session 挂住写事务，后续整文件 `database is locked`（锁源是残留会话不是残留数据，按前缀清行治不了）。
- **测试文件把 bag 表清空到 0 行会触发 demo 数据重播种**：`bootstrap.seed_demo_data` 原守卫是"表非空即跳过"，清空后下一个 TestClient lifespan 重插 demo bag 且撞 `scene.name` 唯一约束（IntegrityError 500，后续所有页面测试连锁失败）——守卫已改为按 `DEMO_BAG_UID` 存在性判断；写会清 bag 行的测试时预期"demo 行可能被重播种"，断言别依赖"表里只有我建的行"。
- 改动面较大或涉及前端/Compose 时跑 `./scripts/local_quality_gate.sh`（无 Docker 才可 `--skip-compose`，Ruff/编译/pytest 不可跳）。
- **新增/修改 alembic 迁移（含他人合入、你要部署的 main HEAD 里的）不要以 SQLite pytest 全绿为放行依据**：MySQL 8.4 拒绝 `TEXT NOT NULL server_default(...)`（1101）和超 3072 字节的宽 TEXT/VARCHAR 唯一索引（1071），SQLite 两者都静默接受。迁移改动后的本地门禁必须补一道：起与 compose 同版本的隔离 MySQL 容器实跑 `alembic upgrade head`（或依赖 `local_stack.sh up` 全新建库步骤兜底，它跑真实 MySQL 8.4）。TEXT 列要默认值时用 model 的 Python `default`（不产生 DDL DEFAULT 子句、DB 无关）；宽路径列要做唯一约束时对规范化路径算 `hashlib.sha256` 存短列再建索引（不要用 DB 生成列——SQLite 无 SHA2()）。**宽列（如 1024 字路径）同样不入普通复合索引**：1024 字 VARCHAR 进 utf8mb4 复合索引 = 4096 字节 > InnoDB 3072 上限，建索引报 1071，SQLite 静默接受——模型 `Index(...)` 与迁移 `op.create_index` 两处必须同查，定位查询改走 sha256 摘要短列的单列索引。多会话专项并行开发时：新迁移提交前查 main 最新迁移链取下一个编号（协调者按任务分配号段，他人可能在途占用相邻编号），不与他人并发改 alembic 链；他人已交付表字段不够用时回协调者排序，不直接改他人迁移。**同族坑不止 DDL：DML 里 `text()`/f-string 拼 SQL 投影时把双引号当标识符定界符写死（`SELECT "event_id", ...`），MySQL 默认 sql_mode 下双引号是字符串常量、投影出字面量而非列，SQLite 把双引号当标识符静默 fallback——查询层不报错、值全错，全绿 pytest 照样遮住**；涉 MySQL 的 SQL 一律用 Core 列对象/`table.c.col` 按方言渲染标识符（或反引号），验收时在真实 MySQL 隔离库 SELECT 出投影值核对是真列值而非字面量。
- **隔离 MySQL 全矩阵事务验收（不止迁移）要写成带守卫的可重复 pytest 入口，不是一次性命令**：env 必须显式给 `*_MYSQL_TEST_URL` + `*_MYSQL_TEST_VERSION_PREFIX`；host 端 PyMySQL 对隔离容器持续 1045（caching_sha2 桥接环境坑）时不要反复重试建用户/改插件/升降级 pymysql：改把 alembic 放进与 MySQL 同 docker network 的 python 容器跑（`docker network create X`；MySQL 容器 `--network X` 不带 `-p`；`docker run --rm --network X -v <repo>:/work -w /work -e DATABASE_URL='mysql+pymysql://<user>:<pw>@<mysql容器名>:3306/<db>' <python镜像> bash -c "pip install -q -r requirements.txt && alembic upgrade head"`），DDL 核对仍用 `docker exec <mysql容器> mysql -e`（容器内走 containerd 内网不受桥接影响）；跑前 `docker ps --filter name=` 确认 Up（Created 状态远程也报 1045 易误诊）。另：本仓迁移链首文件 upgrade 含 `sa.inspect(bind)`，`alembic upgrade --sql` 离线模式必抛 NoInspectionAvailable、生成 DDL 不完整，不能当渲染证据。fixture 先连上核对 server `@@version`/当前库名/端口与 URL 一致（不符或 env 缺 → 整文件 skip 而非 fail，全仓门禁保持绿），杜绝误配 env 打到业务库。写这类测试的坑（本会话全踩过）：裸 `text("INSERT ...")` 不应用 ORM 的 Python 侧列默认，MySQL STRICT 下 NOT NULL as conn:`（隐式事务、退出自动回滚并释放行锁）；`SET SESSION innodb_lock_wait_timeout=N` 写在 begin 外会先触 autobegin、与后续 `begin()` 冲突——放进 `with conn.begin():` 块内作首条语句；行锁竞争断言用"A 持 FOR UPDATE，B 带短锁等待超时拿 1205（互斥证据），A 回滚后 B 插值形态。
- 事务原子回滚的数据库层证据不需要完整 service 入口：同构单事务（先删行→再插违反唯一约束的行→catch IntegrityError→rollback）后断言先前删除的行全部恢复即可——service 编排逻辑由 SQLite 测试覆盖，隔离 MySQL 只验 SQLite 不建模的 InnoDB 语义（行锁/unique/DDL/大表）。
- **`app/main.py` 受 `tests/test_app_structure.py` 硬约束：≤30 行且不得有顶层函数定义**。给它加 exception_handler、中间件或注册逻辑时，把实现放进 `app/web/errors.py`（已有 `register_error_handlers(app)` 模式），main.py 只留一行调用——违反约束的门禁报错晚且抽象（`test_main_is_only_application_assembly`），先把约束当设计输入再动手。
- 门禁的 Ruff 阶段扫的是**整个工作区**，不是你的 diff：被别处未提交文件挡住时先确认报错文件不属于本次提交（`git show HEAD:<file>` 对照行内容），可对那个文件做纯换行 `ruff format` 解卡并跑其受影响测试确认无影响，但**不要**把该文件纳入自己的 commit。
- **自己跑 `ruff format`/`ruff check` 时严格限定在门禁范围 `app scripts tests`，不要把目录扫进任务范围外**（如 `alembic/versions/`）：格式化工具对目录内既有文件会实际改写（重排长行/补空行），`git add -A` amend 后这些无关既有文件就混进了你的 commit，违反范围单一。只改自己的新文件时用 `ruff format <单文件>` 精确指定。同类坑：即使目录在门禁范围内，**也不要对任务域外的模块目录跑 format**（如只改 spray/decode.py 却 `ruff format app/scene/spray`）——格式化会实际改写目录内既有文件（本仓文件常带未格式化的长行），越界文件混进 diff 后污染增量 OCR 批次（协调者按 base..head 整段审）并破坏专项边界；format 后 `git status` 核对改写清单，非本任务逻辑改动的文件一律 `git checkout <base> -- <file>` 还原。配套防线：**每次 amend 后跑 `git diff <base> HEAD --stat` 对照完整文件清单**（不是只看 `git status`），发现被误扫文件 `git checkout <base> -- <file>` 还原后重新 amend。
- **A100 SSH 传输层设计**：每轮多开连接在高负载下必被 sshd 限流随机断连（症状 `kex_exchange_identification: Connection closed`，rc=255）。状态读取合并成一次连接（多条远端命令拼进单条 `sh -c`，多行 JSON 用 `base64 -w0` 单行传输）；只读命令通道（cat/find/状态读取）加瞬断重试（rc=255 且 stderr 命中连接级特征才重试，远端命令自身退出码不重试），写命令通道必须不重试（副作用防双执行）。**轮询状态机里一次"NOT_STARTED"读取不得立即判死在途 run**——传输失败会被误读成 NOT_STARTED 时，判死前需连续 N 轮确认并显式区分"读失败"与"真未启动"，N 用生产配置参数推导（轮询间隔×确认轮数需大于远端写状态文件的最长空窗）；重试前必须先对账远端终态，避免并发写同一 run_root。只读重试通道必须**强制 `capture=True`**（不向调用方暴露 capture 参数）：瞬断判定靠 stderr 文本识别连接级特征，`capture=False` 时 `CalledProcessError.stderr` 为 None，判定永不命中、重试静默退化为单次执行且无任何告警。远端读命令（`find`/`cat`）不得带 `2>/dev/null || true` 类吞错尾巴：它把连接失败变成"成功+空 stdout"，上游把空结果误报成"数据缺失"（掩盖真实故障、诊断方向全错）——空结果必须当失败路径处理（重试、抛错时带 rc/stderr 诊断），绝不静默返回空集合。瞬断的第二层加固是**连接复用**：`ssh_base` 带 `ControlMaster=auto` + `ControlPath=~/.ssh/a100-ctl-%r@%h:%p.sock`（按 用户@主机:端口 隔离）+ `ControlPersist=300`，数百条批量只读共享一条已认证 socket、不再经 MaxStartups 未认证队列；`ControlMaster=auto` 无 master 时自动降级为普通连接，行为不变。ssh 客户端与 rsync `-e` 传输串必须带**同一组**控制选项（共用 `SSH_CONTROL_OPTIONS` / `SSH_CONTROL_OPTIONS_SHELL`），否则两边各建 socket、批量场景限流依旧。落地后真实冒烟（第一次连接建 master → `-O check` → 经 socket 的新连接 → `-O exit` → 确认无 socket 残留）；`-O check/exit` 的 `%r@%h:%p` 占位符不展开，必须用展开后的真实路径显式传 `ControlPath=`。socket 落点是运行方 home 的 `~/.ssh`（代理在生产跑在处理机宿主，权限 700 的 `.ssh` 目录是其前置条件，落地前先 `ls -ld` 确认）。
- **流水线模块给 deps/函数补只读重试通道的接入模式**（修"批量读全裸奔"类事故通用）：① 可选字段放 dataclass **末尾**（`ssh_read: … | None = None`），位置构造 100% 向后兼容，测试里 SimpleNamespace 夹具无该属性时用 `getattr(deps, "ssh_read", None)` 兜底回退；② 加 `_read_ssh(deps)` helper 单点收敛读/写通道选择，所有**只读**调用点（状态轮询、cat 状态/清单、质量门禁 test、日志 tail、批量枚举+逐条读）逐一换到读通道，**写通道原样不动**（副作用防双执行是不变量）；③ 单测断**通道边界**而非重试行为——注入后写通道 stub 一被调用即抛错、api 写回不受影响（重试/非重试语义是读通道底层函数的职责，其单测独立存在，在消费层再 mock 一遍无意义）；④ 改完红绿验证（撤掉 helper 调用应红）。⑤ 批量读函数签名加 `ssh_read=None` 关键字参数（不占位置序），函数内 `reader = ssh_read if ssh_read is not None else ssh`，调用点显式传读通道。跨多层 SSH（开发机→处理机→A100）跑 python 诊断时嵌套引号/heredoc 必炸：写脚本文件 `scp` 到处理机再 `ssh 'python3 /tmp/x.py'` 执行，不要把长 python 内联进多层引号。同类坑：`docker cp /tmp/x.py <backend容器> && docker exec <c> python3 /tmp/x.py` 跑 app 相关脚本时 `sys.path[0]` 是 /tmp 而非 cwd，`from app...` 报 ModuleNotFoundError（同一文件 `python -c` 内联却正常，易误诊成环境坏）——import app 前 `sys.path.insert(0, "/app")`。生产库定向小范围清理（如按 operation 前缀删若干 `api_idempotency` 行）也用此形态：脚本先查数打印（删前/删后 count + 关联数据 count 证明未误伤）再 commit，审批话术报精确行数与过滤条件。
- 给轮询型 pipeline 函数（如 `start_or_reconcile_phase1`）写测试桩时用恒定返回值的 lambda；`iter([...])` 耗尽抛 `StopIteration`，会被轮询循环的 `except Exception` 吞掉，测试表现为无报错地挂到 timeout，极难定位。
- 改 pipeline 错误文案（`*_FAILED: ...` RuntimeError）前：grep 测试树里对旧文案的断言（retry_policy、pipeline_api 用例常引用具体字符串），并保留自动重试策略依赖的关键字——`app/domain/retry_policy.py` 靠大写后的 `EXIT CODE -9/137` 识别 OOM/SIGKILL，文案里 `exit code N` 字样不能丢。
- 解析 `git status --porcelain -z` 等 git 二进制输出时：Python 3 里 `b"R "[0]` 是 **int**（82），`in (b"R", b"C")` 恒为 False 且无报错——用切片 `entry[:1] in (b"R", b"C")`。且 `-z` 模式下 rename/copy 是**两个 NUL 片段**（`R 新路径` + 裸旧路径，非 `old -> new` 单条），必须成对消费只审新路径，按单条循环会误抛异常或把旧路径当独立条目。这类静默逻辑错误用临时 git 仓库 + `xxd` 看真实输出再写解析。
- 改 pipeline 执行代理脚本（`scripts/phase0_host_proxy.py`、`scripts/self_built_pipeline.py`、`scripts/nvidia_pipeline.py` 等）的失败处理时，本地 mock 栈（`local_pipeline_proxy.py`）不经过真实代理代码，端到端验证不到新文案；改用函数级直接驱动验证，做法见 `references/proxy-scripts-verify.md`。
- **`scripts/` 下模块加新顶层导入前先查所有直接启动路径**：`a100_host_proxy.py` 对 `scripts/` 模块有两种导入形态——`from scripts.xxx`（repo 根在 sys.path）与 `from xxx`（systemd ExecStart 直接跑脚本，sys.path[0]=scripts/、**repo 根不在 sys.path**）。在被直接启动的模块链里加顶层 `from app.` / `from scripts.` 导入（如给锁模块加 `from app.services...`、给 `self_built_pipeline` 加 `from scripts.bag_writer_lock ...`）会让 fallback 分支直接 `No module named 'scripts'/'app'` 崩在启动，而 pytest 永远从 repo 根跑、定向测试测不出来（本会话被 ocr 判 critical）。正确形态：导入方 `try: from scripts.X import ...; except ModuleNotFoundError: from X import ...`，app 依赖模块侧 `try: from app...; except ModuleNotFoundError: sys.path.insert(0, parents[1]); from app...`；提交前用**直接模式导入探针**验证（subprocess 清 sys.path、只插 scripts/，import 目标模块）——探针复现后再修。
- **代理本地步骤里 data_root 可能本地（NAS 挂载）也可能远端（A100 ssh）时，每个文件访问点——目录枚举、读文件、文件校验——都要按 locality 选择分支**（沿用现有回调注入模式）：纯 `Path.iterdir()/is_file()` 写"只"会漏枚举点，且默认配置常恰好走远端分支（如 test 环境 frames 功能开启 + 不发 NAS），生产首跑即崩。回归测试必须含一个"本地不存在的远端路径 + ssh 桩"用例驱动同一公共入口，证明远端分支可走通——这类 locality 遗漏靠 ocr 也能抓到（high），但测试先抓最省。**分支谓词函数本身（如 `_is_local_path`）必须直接单测真实实现**：mock 掉谓词只测分支消费逻辑，谓词自身缺陷（如函数体调了 `Path.exists()` 却丢弃返回值、末尾 `return True` 恒真）单测永远绿、生产首跑即崩——修谓词后加"真实存在的本地路径 → True、不存在的远端路径 → False"两个直调断言，并用红绿验证确认测试真能拦旧实现。同理，代理脚本向 backend 上报的 `artifact_type` 等字面量是跨进程边界契约，backend 侧要有"所有代理字面量 ∈ backend 枚举"的契约回归测试——全 mock `deps.artifact` 的单测对枚举缺失恒绿，只能生产首跑 422 才暴露。
- 多个回调桩共用一个 `calls` list 时 arity 会混（如 `deps.api` 3 元组 + `deps.step` 2 元组）：断言前先按 `len(call)` 过滤再解包，否则 `for a, b in calls` 在 3 元组上抛 ValueError；更稳的做法是每个回调各用一个 list。远端分步 JSON 是多行 indent 格式，经 SSH 进按行解析的循环要 base64 编码单行传输（`base64 -w0`），直接 `cat` 会被换行截断。
- 轮询闭包里做"签名未变化则跳过远端读取"的缓存时：缓存值必须与本轮新建的 tuple 同型（`last_sig: tuple[str,str] | None` + `nonlocal` 更新）；用 `[None]` 列表容器包一层后写 `if sig != last_sig` 会拿 tuple 比 list 恒为 True，跳读完全失效——此类 bug ruff 不报，靠断言"跳过场景远端读取次数不增长"的测试用例直接抓。
- Pyright 不在 `or` 右侧收窄：`data.get("x") is None or int(data.get("x"))` 仍报 `int(None)` 类型错。先 `v = data.get("x"); if v is None: continue` 再 `int(v)`。ruff 与 Pyright 检查面不同，两者都要过。
- 脚本类 CLI（JSON stdin/exit code 协议）的 `fail(...)`/`ok(...)` 辅助函数必须标 `-> NoReturn`，否则 Pyright 在 `fail()` 之后的 `req[...]` 全报"possibly unbound"。测这类脚本用 subprocess 真实进程 + JSON stdin（与生产调用方式一致），比 in-process import 更能在测试里抓到协议层错误（stdout 格式、exit code、env 传播）；解析 stdout 取**最后一行** JSON（协议约定成功/失败各只输出一行，但 stderr 与进度输出可能混排）。
- 仓库 Session 是 `autoflush=False`：给 ORM 列赋新值后，若后续辅助函数会重 SELECT 同一列（如 `control_plane._ownership` 重查代次列），读到的是旧值——赋值后、store/重查前必须 `db.flush()`。这类缺陷表面是"幂等账写错代次"，只有跨调用链审查才暴露，修后加回归断言"账本列 == 新值"。
- SQLAlchemy 2.0 `db.scalar()` 多行结果抛 `MultipleResultsFound`（正常写路径变 500）：对无唯一约束列（`BagRecord.relative_path` 仅靠 upsert 业务约定唯一）的列投影 select 一律 `db.scalars(...).first()` 并带 `order_by` 固定取值语义。
- `select(...).with_for_update()` 在 SQLite 测试里被静默忽略（退化原行为），本地绿不能证明行锁语义：claim/竞争类修复 HANDOFF 标注"行锁待隔离 MySQL 实证"（T-09 类），不要报"已验证并发互斥"。
- **版本列乐观锁（read-compare-mutate）必须落成 DB 层条件 UPDATE 权威守卫，不能只在内存比 `row_version`**：两请求同读同代次时，内存 `if row_version != expected: 409; row_version += 1; save` 在真并发下双双过检、静默覆盖双 200（此类更新没有唯一约束兜底，IntegrityError 拦不到）——改成 `sa_update(Model).where(Model.id==.., Model.row_version==expected).values(...)` 后查 `result.rowcount`，rowcount==0 → 回滚本事务已写内容 + 409，只有一个能命中。**守卫 UPDATE 前不得对同一行有 ORM 属性赋值 + flush**：失败会话里 ORM 层 stale 对象的 autoflush/显式 flush 会先于 rowcount 判定执行，抛 `StaleDataError` 冒泡成 500，`rowcount==0 → 409` 分支实际不可达（隔离 MySQL 双独立会话同代次并发实测坐实）——正确形态是把内容列与 `row_version+1` 合并进**同一条**守卫 UPDATE（`values(col=..., row_version=row_version+1)`，守卫命中必 modified、affected≥1；输方 0 匹配走 rowcount==0），UPDATE 带 `execution_options(synchronize_session='fetch')` 作兜底，再补一层 `except StaleDataError → 409 同口径回滚` 防残留路径。测试侧注意：SQLite 单线程无法自然触发该真并发窗口，回归只验用户可见契约（旧代次请求被 409 拒、内容不被覆盖），真并发互斥与 `with_for_update` 同等待"隔离 MySQL 实证"——**实证由协调者双独立会话竞争复测（验收标准不接受"SQLite 单会话无法实证"为终态）**，HANDOFF 如实标注别报"已验证并发"；本地能补的是 monkeypatch 在 execute 层强制 `rowcount=0`、在 flush 层抛 StaleDataError 的分支回归（红绿申报）。
- 一个资源按多版本设计（唯一约束 `(id,version)`、seed `max+1`、多处按活动版本折叠）时，**新增/改任何"按某键定位单条"的读路径都要核对是否也做了活动版本折叠**：漏掉某一处（如匹配函数直接 `where(enabled=True).all()` 无 ORDER BY）→ 版本升级后旧 enabled 行同键先命中，下游把旧 version 嵌进幂等/占位键，产生重复系统行 + 错误版本事件。修法是抽一个 `_active_*` helper 统一折叠口径，所有定位点复用同一 helper，别各写一份内联逻辑（内联副本迟早和主路径漂移）。
- **IntegrityError 语义化 409 前必须回读确认撞的是哪个唯一约束**：表上有多唯一约束（如 claim 占位键 + 主键 id）时，flush 冲突不一定是预期竞争——把撞别的约束（id 复用等真实后端故障）也统一映射成"占位竞争 409"，客户端会无限重试、真实问题永不暴露。except 块先 rollback、按预期竞争持有者（带状态过滤）回读，命中才转 409，未命中 re-raise 让故障以 500 暴露；savepoint（begin_nested）包住 insert+flush 是配套形态。回读缺失时别在注释留"回读确认后转 409"的承诺——注释与实现漂移是 ocr 轮次反复抓点（本会话返修时简化掉了回读、留着旧注释，第三轮被报）。
- 写"过期"测试用例时把过期时间拨到确定早于 TTL 的值（TTL=300s 拨 -3600s）：只减几秒仍在未来，分支没走到，失败报告是裸的状态码不符（202≠409），排查要绕回拨值量才发现问题。
- **"回读确认后才转 409"这类注释承诺必须与 except 块实现对账**：返修时把回读逻辑简化掉但留着承诺性注释，会被后续 ocr 轮次按"注释声称的行为代码没做"再报一遍（同类：注释说"按 X 重试"实际走通用重试）。改异常处理块后 grep 同函数内"回读/确认/按"等承诺词逐句对照实现。
- 安全/fail-closed 类修复的回归测试要做**红绿验证**：临时撤掉修复块跑新用例确认 FAILED（红），恢复后确认通过（绿），防止测试断言写宽导致假通过（如把错误详情文本断言成固定码、把"状态文件应存在"写成"不应存在"）。撤改-恢复用 `cp` 备份到 /tmp 再还原，别靠手工编辑回滚。
- **同一测试里 pytest.raises 断言了服务层异常后、要复用同一 session 时必须先 `db.rollback()`**：非 HTTPException 的服务端异常抛出后 session 事务进入污染态，后续查询返回 stale 结果（应命中的 match 查询查不到、分支静默走 `matched:False`），症状像"第二段行为莫名变了"且直接复现脚本一切正常。真实流程每请求新 session（get_db yield），此坑只在"失败后继续用同一 session"的测试序列出现——两阶段测试（create 抛错 → bind）在阶段间回滚，或各阶段用独立 session 断言。

## 远端锁脚本（flock / nohup holder）的测试
- 测 `sh -c` 下发的锁脚本时，fake ssh 对 `sh -c` 命令**真实本地执行**（cwd=tmp 目录），其余业务命令只记录——验证的是真实 flock 语义而非字符串内容。互斥的直接证据：持锁窗口内独立 `exec 9>lock; flock -n 9 && echo FREE || echo HELD` 探针对 HELD，退出后 FREE。pytest 下**不要**用"起第二个后台 holder + 文件轮询"证互斥——独立进程稳定、pytest 环境时序敏感且难诊断；一个独立 flock 探针即可作权威证据。
- 启动锁（后台计算持锁）顺序是硬约束：`exec 9>lock; flock -n 9 || exit 42` 必须位于**幂等早退检查之后**（已有活 PID 不必抢锁）、**nohup 之前**——后台子进程继承 fd 9，父退出/SSH 断开不释放，锁随子进程退出。回归测试用真实 `nohup sleep N &` + 父脚本退出后探针 HELD、等子退出后 FREE 验证继承语义。
- python 生成 bash 脚本（heredoc 写 holder + nohup 执行）时：`cat > ... <<'EOF'` 的目标与 nohup 的脚本路径必须是**绝对路径**（nohup 后台进程的 cwd 不确定，相对路径静默找不到文件）；会话标记目录放在 `lock.parent / "sessions" / <lock名> / <session>`——锁文件的 stem 是文件名不是目录，往 stem 后面拼路径会指向不存在的位置。
- **长计算后台 holder 持锁的 TTL 必须是"失联泄漏窗口"语义，不能是"计算上限"语义**：holder 的 TTL 若等于最坏计算时长，计算超时时 holder 会 TIMEOUT 释放锁而本地进程仍在写——删除方此刻可拿到同一把 flock，互斥被**静默**打破（本会话 ocr medium，真 bug）。正确协议：本地存活进程用续租线程周期性 `touch renew`（间隔 ≈ min(上限, ttl/3)），holder 每轮见 renew 重置 idle 计时；TTL 只在连续无 renew（本地崩溃/失联）后触发自行释放，作防泄漏兜底。回归必须两侧都有："本地存活、工作时长数倍于 ttl、探针全程 HELD"+"本地停止续租、holder 在 ttl 内 TIMEOUT 释放"。同理，不同失败模式的错误码不得复用（holder TTL 过期与本地等待就绪超时曾共用一个码，调用方无法区分可重试语义，对账失效）——每个模式独立码。
- 只读诊断端点（status/inspect）与破坏性 execute 并存时，**两者必须共享同一套对账/作用域核对逻辑**：诊断给绿灯而 execute 拒绝（fail-closed）会让操作者按错误信号决策。身份记录按比操作更粗的键存储时（如按 bag 一份记录、cleanup 按 cleanup+digest 一份状态），诊断端必须逐字段核对作用域（identity/generation/digest/pid），不符时报"证据不足"并原样保留记录供人工核对，不得报通过。
- 反复 patch 缩进把一段生成/抽取的大代码块改乱（IndentationError 连环出现）时：停止就地修，`git show HEAD:<file>` 恢复原始文本，把全部修改重建为**锚定式显式字符串替换**（每处 `assert old in src` 后 replace，逐条验证）——逐行修缩进会把嵌套层级越修越错。

- **CSS transition 在自动化浏览器里不推进**：headless 环境加类后读 `getComputedStyle`，transition 中的属性（opacity）永远停在起始值，等再久也没用——规则已命中不能据此判失效。用同一条规则里**无 transition 的属性**（如 `pointer-events: none` 即时生效）作为命中证据，再核对 `document.styleSheets` 里 selector 确实匹配目标元素。
- **移动端响应式验证用 CDP 改真实视口**：`cdp("Emulation.setDeviceMetricsOverride", width=390, height=844, deviceScaleFactor=2, mobile=True)`，测完 `clearDeviceMetricsOverride`。必须先按真实交互路径打开元素（点触发器）再缩视口并 `dispatchEvent(new Event('resize'))` 触发同步逻辑；直接 JS 设 `hidden=false` 绕过打开流程，量出来的是未初始化状态，结论无效。判据用 `getBoundingClientRect` + `getComputedStyle`（width/position）+ `document.documentElement.scrollWidth` 是否溢出视口。

- Bag 清理全链路浏览器验证用自包含入口 `scripts/run_bag_cleanup_browser_test.py`（模式同 `run_bag_search_browser_test.py`，不依赖 local_stack.sh compose 栈）：临时 SQLite + seed 多 bag（成功/部分失败/刷新恢复/取消）+ uvicorn backend + **真实 worker**（local transport 真删临时树）+ 故障注入协调线程 + 无头 Chrome mjs（`scripts/bag_cleanup_browser_test.mjs`）；文件级断言（目标真删/取消保留/NAS 哨兵）放 Python `verify_final` 读同一 manifest，浏览器只看 UI 状态。
- **`app.config.settings` 是主进程单例、在首次 `import app` 时按 `os.environ` 冻结**：harness 里必须**先设全部 env（DATABASE_URL、ENVIRONMENT、BAG_CLEANUP_*）再首次 import app**（哪怕是调 `approved_roots_for`）。踩坑症状：seed 写进默认空库、backend 读 0 行、preview 404 "source not found"——极易误诊成 seed 夹具 bug，先查 import 顺序。
- **worker claim 租约 `ttl=120` 硬编码（主循环 `ttl_seconds=120`），confirm/retry 都不重置租约**：同一 cleanup 的下一阶段要等上一行 lease 过期才可 claim（INSPECT→EXECUTE 实测 +120s 死区；不同 cleanup 互不阻塞）。浏览器/curl 驱动等待阶段流转时**每个阶段超时必须 >120s**，否则"部分失败未触发"假阴性。阶段时间线以 worker.log 的 `claimed <id> phase=... gen=...` 行为唯一权威，等超时从它推导。
- **"部分失败"确定性构造 = FIFO 文件**（holder 删除 FIFO 必失败 → PARTIAL/NEEDS_RECONCILIATION；本机 fs 不支持 `chattr +i`，别用它）。FIFO 必须**在 PREVIEW_READY 之后、confirm 之前**（即 EXECUTE 窗口内）创建：提前建会被 inspect 标 `contains_mount` → MOUNT blocker、连 confirm 都走不到；盲目高频写删竞 holder 窗口则不可靠。用 Python 协调线程轮询 mjs 写的控制文件（ctl/ 目录）注入/移除，移除后 retry 续删到 SUCCEEDED。
- 防双击断言：`Page.addScriptToEvaluateOnNewDocument` 在 bag-cleanup.js（defer）执行**之前** patch 原生 `fetch` 计数 POST /confirm——双击确认后应恰好发 1 次。同一模式用于"retry 恰好发 1 次 /retry"断言，但注意**计数器在整页 reload 后重置**：SUCCEEDED 路径会触发前端整页 `location.href` 重载，计数读取必须放在 reload 发生之前（点完按钮的同一文档内），否则读到的是新文档的 0。相邻场景间也要做一次干净 `navigate`：前一个场景的 SUCCEEDED reload 会残留页面内 state（busy/cleanupId），下一个场景直接点行按钮会走 resume 分支而非新发起 preview，断言对象整个错位。
- **worker reconcile "无进展"热自旋会挡死用户 retry**（已修：reconcile 全 UNKNOWN 分支有界退避，改 worker 主循环时守住此回归）：reconcile 全 UNKNOWN 汇报会清租约 → 行立即可再 claim → 主循环无 sleep，~17 次 FOR UPDATE claim/秒，行在 REMOTE_DELETING/NEEDS_RECONCILIATION 间反复翻；retry 要求行停在 NEEDS_RECONCILIATION，几乎必撞 409 永远落不了地。症状：worker.log `claimed ... phase=RECONCILE gen=N` 每秒重复且 gen 不前进、DB 状态文件 PARTIAL 却无 EXECUTE gen+1。规则："汇报结果 + 释放租约"的轮询循环对**无进展分支必须有界退避**（worker `RECONCILE_STALL_BACKOFF_SECONDS=3s`）；闭环里 retry 长时间不落地先查 worker.log 是否热自旋，别误诊成前端 bug。
- **CDP 自动化："勾选 checkbox 启用按钮 → 点按钮"必须在同一次 `evaluate`（单个事件循环 tick）内同步完成**：清理弹窗 ~2s 轮询重渲染会重建 DOM、把 ack checkbox 重置回未勾选（按钮重新 disabled），两次独立 evaluate 之间留的窗口必被重置。写成单个 IIFE：`checkbox.click() → assert !button.disabled → button.click()`，外层套有界重试（300ms 间隔），循环内先查 rowGone 防无限自旋。写"点击→成功"类 AC 的断言要防**弱断言**（ocr 常抓的 medium）：仅断言"点击落地"（按钮不可用/点击返回成功）不足以防其他完成路径冒充该 AC——终态行消失可能是别的流程删的；必须同时断言该 AC 专属的动作证据（fetch 计数器恰好 1 次、worker.log 出现 `phase=EXECUTE gen+1` 这类代次前进行）。
- **下发资源为当前版本的验证用逐字节比对**：独立栈 mjs 里 `fetch('/static/<file>').text()` 与仓库对应文件（manifest 里带 `repo_root` 锚点）全文比对，不要只 grep 新片段——独立栈无镜像构建层，字节一致才是版本证据。
- CDP mjs 骨架可直接复用 `scripts/bag_search_browser_test.mjs` 的结构：`--remote-debugging-port=0` + 轮询 `DevToolsActivePort` 拿真实端口 + `/json/list` 找 page 目标 + WebSocket 消息分发；页面断言失败时抓 `bc_e2e_failure.png` 再退出。
- **长跑 E2E（>10min）用 `background=true` 且输出重定向到 scratch 日志文件，不要 `| grep | tail` 管道**：管道把全部输出缓冲到进程退出才可见，后台进程的输出预览恒为空，看起来像没跑；终端前台 >600s 也会被自动升级成后台跟踪进程。进度判据一律用落盘制品而非进程 stdout：栈 tmp 目录的 `worker.log`（`claimed <id> phase=... gen=...` 是阶段流转唯一权威）、`ctl/` 控制文件、`bc_e2e_*.png` 截图序列的增长。
- **mjs 里每个等待必须有界**（waitUntil 带 timeout 或循环带次数上限 + 最终 assert）：裸 `while(!done)` 重试循环在竞态不满足时表现为"无限运行"而非报错，配合上一条的空日志会让人误判"还在跑"——卡住无错误时先查制品，再怀疑无限循环。

## Bag 清理真实 A100 测试根 E2E（ssh transport 真实删除）
- 用户授权"真实测试环境测试全流程"时：入口 `scripts/run_bag_cleanup_real_a100_test.py`（仓库内），A100 测试根 `bag-cleanup-exec/` mini repo + 真实 worker（ssh transport、门禁+authorize secret 开启）真删 tag 命名新生成夹具，约 12-15 分钟（租约节奏），完整装配规则/场景断言/跑后复核见 `references/real-a100-cleanup-e2e.md`。最贵的五条坑：
  - **bag 清理 API 非浏览器驱动**：preview/confirm/retry 路由返回 **202**（断言别只认 200）；confirm/retry 前 GET 必须 `?regenerate_nonce=true`（否则 nonce=None→422）；`start_preview` 只在请求 cookie 同 session 时复用会话——驱动建多个 op 必须把首个 preview 的 Set-Cookie 带给后续 preview POST，否则每个 op 绑独立 session、跨 op 读**静默 403**，wait_status 循环到超时零报错（症状：DB 全 PREVIEW_READY 但驱动读不到）。
  - **EXECUTE 被拒（LOCKED 等）不上报、在途再仲裁 ~120s 自动重驱**：阻塞解除后自动收敛 SUCCEEDED，**不需要用户 retry**（PARTIAL 路径才要 retry）。互斥验证证据=worker.log `rc=5 EXECUTE_BLOCKED ... flock held by another process` + 持锁期间零删除断言 + 释放后收敛。
  - **ssh 上不起长驻后台进程**：`nohup X &` 让 sshd 通道等后台 fd→客户端超时连 X 一起杀；正确 `X >/dev/null 2>&1 & echo $!` 经 Popen 取远端 PID、ssh 退出，释放 `kill <pid>`；持锁验证用独立 `flock -n` 探针（应失败）。ssh 上 `pkill -f <模式>` 若模式出现在自己的远端命令文本里会自杀（空输出无报错）——按记录的 PID kill。连续短 ssh 连接会触发 A100 远端限流（"kex_exchange... Connection closed"）：操作合并单次 ssh + 连接关闭特征重试。
  - ssh transport EXECUTE 无 `BAG_CLEANUP_AUTHORIZE_SECRET` fail-closed（INSPECT 放行、EXECUTE 拒）：worker 签 token、A100 executor 验签，两侧必须同一 secret（内存随机 hex，经 REMOTE_CMD 的 `VAR=x cmd` 远端 shell 注入）。
  - 长跑 E2E 驱动布 `faulthandler.dump_traceback_later(300, repeat=True)`：/proc fd/wchan 采样对卡死定位不可靠（sleep 间隙 fd 表无 socket、do_select≠卡死），watchdog 直接转储栈到 run 日志钉住等待行。
  - 成功删除后嵌套目标留空壳目录：清理按 tag 通配覆盖 5 个根模式，对照**跑前 5 根快照+mtime** 复核（既有条目是数天前的，不匹配自己 tag 就不是你删的）。

## 前端资源/模板改动（CSS/JS/模板）
- 静态资源与模板都是构建时打进镜像（无 bind mount），改完不重建浏览器看到的仍是旧内容——这是最常见的"改动没生效"假象。先确认服务的是新版再测功能：`curl -s http://127.0.0.1:8181/static/<file>.css | grep '<新片段>'`（前端资源）；模板改动则 `curl -s 'http://127.0.0.1:8181/<页面>?nc=$RANDOM' | grep '<新片段>'`（重建对象是 backend 镜像，见上节）。
- **新增静态 JS/CSS 文件必须加进 `app/web/rendering.py` 顶部的 `static_version` 哈希**：该 12 位版本拼进所有 `/static/*?v=...` 引用，漏掉新文件时版本号不变、浏览器一直命中缓存（对从未引用过的新文件则 404 被当"无变化"）——症状是"改了 JS 但页面行为没变"。改完 `ls app/static` 对照 rendering.py 的文件清单逐一核对。
- `static_version` 只哈希**文件清单**不哈希内容：只改既有文件内容时版本号不变，浏览器磁盘缓存继续发旧资源——"修复没生效"可能是缓存假象而非修复错误（T-08 ocr 复测时 CSS/JS 改动全部"检测为 false"，根因是缓存+镜像未重建）。核对方式：重建后在页面里 `fetch(url, {cache:'no-store'}).text()` grep 新片段（绕开页面已加载版本与浏览器缓存）；注意 fetch 到旧内容也可能是**镜像没重建**（静态资源打进 frontend 镜像），先 `docker exec <frontend> wc -l` 核对容器内文件再怀疑缓存。
- 图标型按钮（`copy-path.js` 的 `data-copy-icon` 分支，只含 SVG 无文本）的复制反馈**不能走 `textContent="已复制"`**——会把 SVG 清掉且图标永久消失；图标按钮用 class 切换（`.copied`/`.copy-failed`，颜色反馈），textContent 恢复逻辑只留给文字按钮。
- **bag 列表交互有 pytest 之外的硬质量门**：`scripts/run_bag_search_browser_test.py`（临时 SQLite + 种子数据 + 无头 Chrome）实跑 `/bags` 的复制、展开、三档响应式，`local_quality_gate.sh` 会调它。门断言写死在 `scripts/bag_search_browser_test.mjs`（如点 `[data-copy-text]` 等 `textContent==='已复制'`）——改任何 UI 反馈机制前必须 grep 该 mjs 的 selector/行为断言并同步更新，漏了门禁必超时（本类遗漏靠 ocr 才抓到）。改交互后直接 `.venv/bin/python scripts/run_bag_search_browser_test.py` 验证（自包含，不依赖本地栈）。
- **可展开行做键盘可达用 `tabindex` + `aria-expanded` + keydown（Enter/Space）**，不要给行加 `role="button"`：行内含名称链接/操作按钮等可聚焦后代，违反 ARIA"button 不得含可聚焦后代"，ocr 会在"建议加 role"和"要求去 role"之间反复打转。
- 表格/媒体查询给行设 `display:block` 会压过 UA 的 `[hidden]{display:none}`，折叠的详情行再也收不回去（桌面正常、仅移动端暴露）：必须补显式 `.detail-row[hidden]{display:none}`。验证用 CDP 390px 移动视口实测折叠/展开/收起三态。
- 同族坑不限于 display:block：弹窗/overlay 类元素只要 author 层给了任何 `display:` 值（`flex`/`grid` 等）就压过 UA 的 `[hidden]{display:none}`——T-08 的 `.bc-overlay{display:flex}` 缺 `[hidden]` 守卫，弹窗每次加载都挡全页且关不掉（ocr critical）。隐藏元素测试必须断言 `getComputedStyle(el).display === 'none'`，只查 `.hidden` 布尔值会漏掉整类（本会话浏览器实测就是因此漏过）；对照同文件其他隐藏面板是否有 `[hidden]` 守卫是最快的自检。
- 向模板传结构化 JSON 给 JS：FastAPI `Jinja2Templates` **有** `tojson` 过滤器（2026-09-29 实测渲染 `{"a": 1}`，含 HTML 实体转义），放进 `<script id="..." type="application/json">{{ data | tojson }}</script>` 块由 JS `JSON.parse` 读取，比散落 `data-*` 属性干净；纯 data-* 方案只适合少量标量。
- 只改 `app/static/` 下 CSS/JS 时用最小命令重建，不必 `local_stack.sh up` 全栈重建：`docker compose --env-file /dev/null -p rosbag-catalog-local -f compose.yaml -f compose.local.yaml build frontend && docker compose --env-file /dev/null -p rosbag-catalog-local -f compose.yaml -f compose.local.yaml up -d frontend`。改模板/后端代码时同上但对象换成 `backend`；两处都改直接 `local_stack.sh up`。
- 布局/对齐类修复必须用浏览器 `getBoundingClientRect()` 逐元素量 top/bottom/height 对比（可用 browser 工具在页面里 `js()` 执行），不要凭截图目测下结论，也不要改完就报修好；对齐问题的量化判据就是各元素 top/bottom 相等（容差 <1px）。
- 前端 rebuild 后跑 `local_stack.sh test`，revision 对账可能报 `stale=true, changed=[platform]`：这是本地栈 revision 落后于新 commit 的预期信号，全链路仍应到 PUBLISHED；按 HANDOFF 记录即可，不需要额外操作。

## 安全关键路径的 fail-closed 边界
- 非 Linux/无 `/proc` 环境下"进程是否退出"类判断必须返回**证据不足**（None），不得返回"已退出"（True）——`/proc/<pid>` 不存在检查在无 /proc 系统上恒为 False，会 fail-open 放行续删；docstring 承诺的 fail-closed 语义与实现不一致时按实现报错方向（放行危险侧）定级。
- 原子写后"读回校验"的 except 要覆盖 `OSError + ValueError`（json.loads/文本解码失败不是 OSError），归一后再抛 OSError——调用方通常只捕 OSError，漏掉的异常类型会让 holder 崩溃且不留结果文件，对账证据全灭。
- 清理"使命完成"标记文件（holder 身份记录等对账依据）必须发生在**终态记录成功落盘之后**：先清标记后写终态，一旦终态写失败，本可幂等重放的场景会因对账证据缺失退化为人工介入。
- 诊断端点输出字段若注释声称"保留记录供人工核对"，输出里必须真有该字段——注释承诺与响应体不一致会被 ocr 判 low 但属契约背离；同理适用于失败/重试路径的注释（声称"按 X 对账重试"但实际走的是另一条通用对账时，要么实现该路径，要么把注释改成如实描述真实行为，不要留承诺性注释）。

## HANDOFF 与提交
- 本仓库有多个会话并行写入（devflow worker 等会持续改 devflow 文件并往 HANDOFF 顶部插条目）：patch HANDOFF 前必须重读文件顶部拿当前锚点，old_string 用锚点行而非会话开始时的内容，否则匹配失败；commit 前 `git status --short` 核对只 add 本任务文件，提交后用 `git show --stat HEAD` 确认没有混入他人改动。
- **他人未提交 WIP 与自己的改动混在同一文件时，`git add <file>` 会把 WIP 整段带进 commit**（同文件/同行的改动无法按 hunk 拆分 add）。分离流程：`cp <file> /tmp/backup` → `git checkout -- <file>` → 逐处 patch 重放**只属于自己的改动** → `git diff <file>` 确认差异仅剩自己的 hunk → 提交 → 从 backup 恢复 WIP。恢复后必须 `diff -B /tmp/backup <file>` 做到 0 差异 + 文件花括号计数平衡再收尾：用脚本按选择器/模式抽取 WIP 块再追加时，可能丢掉结构性包裹行（如 `@media (...) {` 与对应 `}`），规则会裸奔到全局作用域且 CSS 不报错——不能只数规则出现次数当验证。误提交的 commit 撤销用 `git reset --soft HEAD~1 && git reset HEAD <file>`（保住工作区其余 WIP），重走分离流程。另注意 checkout 后 sibling 可能立刻再写入该文件，重放前后都要重新 `git diff` 核对。
- **四会话文档协作专项（PROTOCOL 约定"执行者禁跑 OCR、协调者 flock 代跑"）里，执行者自跑 OCR 会三重反噬**：(1) 与协调者代跑并发→Qwen 共享队列下双方都超时（本会话 707 行文件整文件审 4 次撞 deadline，协调者改 `--from <旧> --to <新>` 增量模式 ~10min 就过）；(2) 停自己的 ocr 时 `kill $(pgrep -f "ocr review -c <sha>")` 宽匹配会**误杀协调者同 commit 的代跑**（命令行同含 sha），停进程必须核对 PID 的父链/启动目录确认归属，或只杀自己记录的进程组；(3) 同 commit 多轮自跑+resume 会让协调者看到"执行者 OCR 在途"误判 owner 未停手，破坏验收时序。正确动作：交付后**停掉自己所有自跑 ocr（逐个 PID 核实归属）**、在回执补记"自跑已停/误杀声明"、等 decision；增量 diff（<200 行）若必须自审用 `--from A --to B` 而非整文件 `-c B`。
- **OCR历史范围先核归属**：区间含其它会话commit时先界定真实审查范围，准备准确base/head的隔离worktree，再用固定入口；累计diff可能不包含中间被还原的改动，不能声称逐commit全覆盖。
- 派单明确"OCR 不要自己跑、协调者代跑"（多会话专项共享单 Qwen 实例，并发挤单会整批挂死）时，提交后直接报 REVIEW_PENDING 等代跑，不自启 ocr：自跑在忙时是 0 字节日志 + 反复 aborted（findings 不落盘），而协调者空闲窗口代跑分钟级完成——被指令时不要拿自己的重试去抢队列。
- **OCR前置串行检查由固定入口实施**：检查实际OCR进程、global/project稳定锁及原run状态；锁忙或未知在途立即BLOCKED，不起新的等待链，不杀其它owner。
- **紧急生产恢复会跳过 ocr 形成欠账，用户事后问"还有没过 ocr 的 commit 吗"时按会话 commit 链全量审计**：`git log --oneline <会话起点>^..HEAD` 列出、逐个 `git show --name-only` 判代码/文档属性（纯 docs/changelog 豁免），所有未审的代码类 sha 一并补跑，不要只查最近一两个；HANDOFF 记一张 commit→session→findings 的闭环总表（引用 session id 前从 ocr 日志 grep `Session:` 行核实，别凭记忆写）。
- HANDOFF 需要引用提交哈希时避免二次提交：先把 HANDOFF 写入同一 commit（不含哈希或用占位），或在推送前 `git commit --amend` 补哈希。推送后再补文档会多出一个纯文档 commit。
- 提交后同步 `/home/wang/work/doc/todo/vla_self_dataset_pipeline_v1_todo.md` 对应条目：补提交哈希、推送证据、验证命令和真实页面实测结果。
- **多会话并行开发同一新模块（各建 worktree 独立交付）时，收尾回执必须加一节"与他路契约一致性核对"**：逐字段对照另一路的类型/接口（字段名、方法名、结构、限额、hash 粒度），列表给出差异和建议归属（类型 owner 按 DESIGN 分工，不擅自改对方类型去对齐自己），交给协调者合入前定夺权威命名。实测漂移高发点：同一概念两侧各自起名（`parameter_specs` vs `parameter_schema`、`unavailable_reason` vs `disabled_reason`）、方法集不等价（一侧多出区分"未注册/已禁用"的查询方法）、hash 粒度不同（整包 vs 单能力维度，可嵌套但要注明）。限额类常量两侧独立实现时逐条核对数值一致性，不一致即潜在对账 bug。核对时直接读对方回执声明的 worktree 路径下的源码（`grep class/def` 提取签名），不要只看回执文字——回执摘要与代码常有滞后。
- 多个会话并行工作本仓库：声称"已推送"或"未部署处理机"前，先 `git fetch && git log --oneline` 核对其他会话是否已推提交、是否已做过生产部署（HANDOFF 顶部条目为准），并用 `git merge-base --is-ancestor <你的sha> <部署sha>` 验证你的改动是否已随某次部署上线；不要沿用任务开始时的部署状态结论，长任务结束前状态可能已被其他会话改变。发现表述过期时修正 HANDOFF/TODO 并在提交记录中说明。
- 长审查/长验证（如仓库 `.agents/skills/ocr-code-review` 里的 ocr 审查，30min 级）期间用户反复问"执行情况"时，用进度证据回答而非猜测：ocr 的 stdout 是**缓冲**的，落盘日志在整个审查期间可能恒为 0 字节，mtime 不可用；真正的进度在 `~/.opencodereview/sessions/<工作目录slug>/<session-uuid>.jsonl`（记录数持续增长、mtime 新鲜、最新 `llm_request` 的 `filePath` 就是当前在审文件，多文件会被合并成一个审查单元），辅以连接收发计数（`ss -tnpi`）、LLM 端点延迟探针（vLLM 排队慢时用 `llm-service-load-check` 技能）；注意 CPU 低+连接静止可能是等模型生成而非卡死。结束时检查日志里的 `WARNING [review_round_failed]`（某轮 LLM 请求 `context deadline exceeded`）：**exit code 仍为 0**，但对应文件集合的审查不完整——汇报时声明覆盖度与"意见不穷尽"，不要按完整审查下结论。日志出现 `Review complete: 0 finding(s); N of M selected item(s) failed`（per-attempt 报某文件 `timed out -> failed`）是**部分审查**：exit 仍 0，已通过文件的 0 findings 不能当全量闭环——收口动作是对**失败文件**补审（`ocr review -c <sha> --audience agent --exclude '<已审文件的 gitignore 模式>'`，秒级 `ocr review -c <sha> -p --exclude ...` 可先预览选中集确认排没排对），跑到 `N of N` 全过，再汇报"各文件均独立 0 findings"。多个 commit（几十上百个）的批量 ocr 审查不要逐 commit 跑：范围切批 + 后台 runner 的完整流程见 `references/ocr-batch-review.md`。
- **审计他人/历史留下的 OCR 记录（evidence 目录 OCR.md、HANDOFF 审查总表）时，"0 findings" 不能当审查通过**：失败的 session（context canceled / LLM timed out / compaction cancelled）不写任何 comment，与"干净通过"的 session 在 `ocr session comments <uuid>` 下输出**一模一样**（都是 'No comments recorded'）。判据看审查日志的 `Review failed (cancelled): 0 finding(s); N of N selected item(s) failed` 行——N of N failed 是审查**根本没跑**而非跑了没意见，逐条回读每个 session 的 comments 才能分清。session 文件在 `~/.opencodereview/sessions/<启动cwd的slug>/<uuid>.jsonl`，slug 是 **ocr 启动时的 CWD**、不是日志 tee 落盘的证据目录——从错误 cwd 跑 `ocr session comments` 报 `no such file or directory` 是 slug 不对、不是 session 不存在，切到 ocr 实际启动的仓库根再查。
- **OCR失败分类与参数以当前固化规则为准**：max-tokens不拆单文件，0用配置/review模板；字符不能直接比较token，前2轮截止与后6轮压缩不可混判。cancelled/round1/2仅是症状，读manifest终因；resume只复用完成文件，不从失败点续跑。最多一次有根因处理的显式补审，宿主代审不自动解除门禁。详细见协调者ocr-runtime.md、ocr-and-merge.md和16B原始诊断。审查发现逐条复核时可用 delegate_task 并行（每批给台账 JSON 路径 + 判定口径 + "落盘结果文件"要求），但**子代理 summary 是自我报告不可信**：它声称"已写 /tmp/xxx.json"或给出的状态结论（如某 run PUBLISHED）必须亲自 `find`/读文件、查库验证后才能采用；结果文件常根本没落盘、状态与库实际不符。收到子代理返回结果时还要**用脚本核对自报计数与实际明细是否自洽**（逐条 recount verdict，比对它报的 total 与列表长度）：曾出现 self-report 的 total/verdict_counts 与随附明细都对不上的情况，不可信计数要按重建的明细重新算，重建时保留每项的标记字段以便复核。子代理撞 max_iterations 上限结束时，通知里的 summary 还会被截断（JSON 数组中途断、计数自相矛盾）：完整 summary 在 `~/.hermes/cache/delegation/live/<deleg_id>/task-0.log` 的 `final` 行里，grep 提取该行再解析；transcript 被截断段用 `sed` 取原始行，不要依赖通知里的预览。
- **ocr 意见处置节奏**：逐条对照当前 HEAD 核实（"当前仍成立/已修复/误报"）后，high 直接修复并补回归测试；low 逐条向用户给出处置建议，**用户批准后才按 ocr patch 改代码**，修复 commit 的 message 注明对应的 ocr session 与 finding；每个修复 commit 按流程再跑一次 ocr（小 diff 分钟级），直到 0 findings 才宣告该 commit 链 OCR 闭环，HANDOFF 记 commit→session→findings→处置 总表。
- **并行会话会在你 patch 期间改写共享文件顶部（HANDOFF.md）**：多会话都往 HANDOFF 顶部插条目，用固定锚点行插入的脚本在锚点被对方挤走后 assert 失败或插错位置。对策：每次插入前重读顶部 5 行，把新条目插到 `# 开发对话交接` 标题之后（最顶部）而不是依赖某条既有锚点；插入后 grep 条目标题确认落位。
- **并行会话会静默回退共享文件（bags.html/bag-search.css 等）的未提交改动**：对方基于旧工作树提交（如 bag-list ocr 返修 `dc2b4a0`）会把你的未 commit hunk 整体覆盖，py/js 等其他文件幸存——极易误判为"改动丢了"或模板没生效。对策：共享文件改动完成后**立即 commit**（哪怕功能未完）；被覆盖时对新基线重新 patch 而非重放旧 diff（对方行内容已变，old_string 失配）；重放前后都 `grep` 抽查关键标记 + `git diff` 核对归属。
- 纯前端/静态资源微调（视觉对齐、样式）没有 TODO 条目，HANDOFF 里写明"不生成候选日志"及原因即可，不强制补 TODO。
- **多任务收尾长跑期间用户问"还有多少/怎么这么复杂"时，先给"剩余 N 项 + 每项工作量/性质 + 下一步决策点"的短表，再问口径（完整 vs 精简 vs 暂停）让用户拍板**：不要继续逐项推进后才解释进度——用户对该仓库的长验证任务（REVIEW 批次）已多次表达厌烦无完期的推进，决策点前置比干完再汇报更省时间。
