# 分叉代码线合并门禁

## When to Use

- 两条或多条线从同一祖先分叉，各自含他人/外部模型/并行会话的提交；其中一条可能已部署到运行环境，但未合主干、未登记任务、未过审查门禁。
- 用户要求的是「梳理清楚 / 能否合入」的证据，而不是立刻合主干。

不适用：单线内部的日常提交与推送，直接用对应仓库的常规提交规范。

## 适用条件

- 两条或多条线从同一祖先分叉，各自含他人/外部模型/并行会话的提交；其中一条可能已部署到运行环境，但未合主干、未登记任务、未过审查门禁。
- 用户要求的是「梳理清楚 / 能否合入」的证据，而不是立刻合主干。

## 原则（每条都适用）

- **先只读取证、后写**：所有合并先在独立 worktree 演练，不切主干分支、不碰用户工作区的未提交改动。
- **授权边界**：合入主干、推送主干、部署运行环境都各自需要当次授权；用户此前的授权不延用。
- **冲突按文件类别解，不按「哪边更新」解**（见步骤 4）。
- **结论即证据**：断言「无回归」必须给出候选与基线两侧同一命令的失败集合，不能只报候选侧数字。
- **线上事实 ≠ 验证结论**：某条线正在生产运行，不构成它通过代码审查与独立测试的证据；两种情况分开陈述。

## 步骤

1. **冻结坐标**：`git merge-base <line1> <line2>`、各线 head、各远端 ref（`git ls-remote <remote>`）。用 `git diff --name-only <base> <line>` 列出每条线各自变更面，确认唯一共同祖先与是否互不重叠。
2. **无副作用预检**：`git merge-tree --write-tree <base> <other>`（不改工作区、不建提交；rc≠0 即冲突）。多条线两两预检，先排掉真冲突面。
3. **worktree 演练**：`git worktree add --detach $T <base>`，再 `git -C $T merge --no-commit --no-ff <other>`。venv 用软链复用主仓环境（`ln -sfn <主仓>/.venv $T/.venv`），不要重建依赖或改动全局环境。
4. **按文件类别解冲突**：
   - **生成物**（部署快照、由脚本生成的清单等仓库明令禁止手改的文件）：取与真实运行状态一致的一侧，不手工拼接；解完按仓库脚本重新生成并核对。
   - **流水/日志类**（HANDOFF、TIMELINE 等历史记录）：两侧都要保留，按时间顺序拼接；用脚本改，不手改，改完再自检。
   - **编号型候选**（changelog / 日志候选条目）：两侧新增同一编号时顺延到下一个空闲编号，状态保持未批准；改完跑仓库的校验与渲染脚本，只接受该条目范围的 diff。
   - **业务代码冲突**：不自行语义裁决，回派该文件的原 owner 做最小返修。
5. **冲突残留自检**：全仓 grep 冲突标记（`^<<<<<<<`、`^=======`、`^>>>>>>>`，排除 `.git`）必须为空。`git status` 干净不等于没有残留标记。
6. **回归等价证明（核心证据）**：
   - 候选树与基线 detached worktree 跑**完全相同**的命令：全仓测试 + lint + 编译/配置解析。
   - 逐条比对失败集合，必须完全一致；新增 passed 应能归因到本线自带的测试文件。
   - 记录两侧 passed/failed/skipped 与 lint 计数作为断言依据。
   - 迁移面：`alembic heads` 必须单头；本线新增迁移单独列出并核对文件名与内容。
7. **越界核**：`git diff --name-only <base> <candidate>` 必须恰好等于本线预期文件集；对不该动的面（API、模型、服务、模板、迁移目录、其他线的文件）逐项声明零改动。
8. **保底与登记**：本线若在任何远端都不存在，先推**备份分支**（非主干）并 `ls-remote` 回读验证；主干 ref 保持不动并回读确认。随后在协作项目里登记任务卡：授权来源与范围、冻结 SHA、变更面、验证证据、门禁状态；再派独立测试，派单里写清**被测固定 SHA** 与只读 worktree 路径。
9. **门禁裁决**：审查或独立测试未收口就不得写「通过」。收口后逐项核对证据再裁决；合入主干与部署各自等当次授权。

## 陷阱

- **只跑候选不跑基线**：失败集无法归因，无法断言零回归。基线 worktree 是必须项，不是备选。
- **审查批次返回「证据不足 / 必须给出条目数组」类结果**时，等于证据不足：既不是「0 findings」，也不得据此判通过。逐批实读原始评论，对照被审查文件的行号核实后再裁决。工具口径收紧导致历史 run 也报同类结果时，不得用新口径推翻此前已接受的结论——先核实再如实报告。
- **换审查身份不得复用旧 run**：更换模型/供应商或审查范围变化都属于新的审查身份，不得用旧 run 的 spec 或结果充当通过证据。
- **不要让未过门禁的线「顺带」通过**：范围外文件、他人未提交改动、其他线的产物都不进本次提交；只 add 本任务文件。
- **不要把选项范围留到结尾或含糊带过**：用户从编号选项里挑一个字，执行后回复要**第一句**点明「正在执行的选项及其范围」，再给证据；否则用户会追问「你是在按 X 工作吗」，含糊就等于没执行。

## 输出格式

- 先给结论与门禁缺项，再给逐条证据（两侧测试计数、lint、迁移头、越界核、远端回读）。
- 明确列出**未执行**的动作及原因（例如「未合入主干、未部署」），以及各自的授权前置。
- 证据用真实命令输出片段，不写「应该/预计」。
