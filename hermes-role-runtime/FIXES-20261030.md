# 原生最终验收与协作机制修复

**开发叶任务全部完成后，需求仍须经过最终集成独立验证和协调者证据复核，才能记为本地验收完成。规划者仍由用户手动触发。**

## 自动接续

接纳需求的冻结材料和有效本地开发策略派生 `COMPLETION_PLAN_PUBLISHED`。开发任务仍归 A/B/C；最终验证和收口是独立的需求级原生节点，不伪装成开发候选。

1. 机械巡检 `workflow_autonomy.sweep` 检查全部供应任务完成、真实合入回执、集成分支和精确提交包含关系，自动建立 `integration_verification` 工作单，无需用户另发派单裁决。
2. TESTER 通过原生准入领取。`verify_integration` 复用现有 operation runner、独立固定 checkout、沙箱、JUnit、证据哈希和 pytest 双次稳定性检查，允许分批取证；MySQL profile 使用已有受控临时 8.4 实例，不接受生产 URL。
3. `deliver_integration` 要求冻结计划中的每个 AC 都有明确结果、执行类型和测试事件引用。未执行、环境问题、skip、失效证据不能证明 PASS。确认代码问题须带唯一问题 ID、原任务 ID 和真实 FAIL 证据。
4. TESTER 及子进程真正退出后，代码问题自动回原 owner 的新 attempt；保留 scope、AC、required_checks 和旧失败。返修仍走自测、独立测试、OCR/适用审查、批准、本地合入及叶任务完成。新集成版本自动再次验证。
5. 最终 PASS 后，协调者 `complete_requirement` 复核当前固定版本、原始测试证据、历史失败处置及在途验证/外部结果，写收口回执和 `REQUIREMENT_COMPLETED`。本地完成与生产启用、真实节点验收、push 分别记账。

缺环境保持 UNVERIFIED，同版本最多三次自动验证工作单，间隔至少五分钟；不无限重跑，也不将环境问题回派成业务代码缺陷。版本/冻结材料/策略撤销变化会关闭通过路径；旧快照安全退出，保留证据。
