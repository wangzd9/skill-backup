# 飞书群消息与进度样式

用于普通回复、READY、任务事件、当前进度与时段报告。仅维护呈现，不创建调度、不代发消息、不决定业务状态或审核权限。频率、静默和事实读取遵循[报告协议](../complex-task-coordinator/references/reporting-policy.md)。

## 先核当前事实

- 模型答复与脚本报告使用同一份当次生成的事实包。模型汇报先运行绑定的 `runtime_tools.py progress-facts --project ROOT --json`，直接读取工具返回的事实正文；不带 `--json` 只返回文件索引，不能视为已读事实。当前事实同时落盘在`inbox/control/runtime/progress/facts.json`；输出截断或尚未看到本次所需字段时，分段读取该文件的相关部分，不声称已读全。按需核对相关原文，摘要不能替代开发、测试和审查的必要证据。长工作结束后、最终汇报前再刷新一次，核对最新相关原文，不把本轮早先读到的状态冒充当前状态。
- 每个事实字段保留来源及有依据的发生、观测、记录时间；群报在重要进度旁给简短来源与时间，完整定位放详情。标题生成时间仅表示本次读取，不是任务取得进展的时间。
- 缺失、过旧或冲突要说明具体缺口。冲突指出两份来源分别说了什么、目前影响及核对动作，不能只写“待核实”，也不能把较新的采集时间当裁决。TODO负责业务任务状态，测试回执负责已验证的行为与版本；任务表未同步不抹去已有测试证据，也不代表获准合入。旧验证与新交付版本不同时，说明已核实的覆盖或具体待核对差异，不能用含糊的“对应版本已通过”代替。
- 不凭 PID 存活、标签 RUNNING、租约释放或无文档变化推断业务成功或空闲。不推算没有口径的整体百分比，不猜 A/B/C 的业务内容。

## 统一样式

- 当前进度首行为 `**协调者：当前进展 YYYY-MM-DD HH:MM +08:00**`，下一行给一句加粗结论；角色名称按实际替换。标题下空一行，使用加粗分区标题，每区下方用单层 `- ` 短条目。
- 一条只说明一个进度、问题或动作。并列事实拆条，不用分号把任务、证据、门禁、计数和下一步挤成一长句。分区不受“全文3–7条”的旧限制。
- 所有角色的用户可见输出都从具体功能及结果重新组织，不能复制恢复摘要、原始事件或旧回执的用语。以派单/事实包确认的功能名开头，再写结果及影响；如没有功能名，使用任务号和已证实的行为，不猜角色分工。“A 叶/三叶/聚合/冻结 head/机械全绿”等内部简称不作为正文描述；例如写“查询功能”“三个功能的联合验收”“交付版本已固定”“指定脚本检查通过”，最后一种还须说明尚缺的业务验证。原始证据、代码、路径和 ID 保持原样，不为呈现改写。
- 关键结论、真实阻塞加粗；路径、命令和必要的短编号用行内代码。正文默认不展示原始状态码、diff 数量、完整 commit、run/grant/call/request ID、原始 token 字典、长路径或长日志；状态写成“正在审查”“已有通过记录，待核对覆盖”等自然语言，需要时给证据详情链接，用户要求才展开。“固定集成SHA”写成“固定集成版本”，“锁空窗”写成“当前审查结束后”；不能为简化表达隐去未通过的门禁。
- 不用 Markdown 大标题、表格、多层列表或全文代码块。允许并要求协调者进度使用多个**加粗分区标题**；不输出 HTML、富文本 JSON 或竖线堆叠的【标题】。普通短答复和单一事件可仅有加粗结论及一两条说明。
- 输出正常 Markdown 正文；Hermes cron final 自动投递，不再 `send_message` 双发。任务名、job_id 等 cron 外壳信息不在正文重复。

## 协调者进度的七个分区

用户要求整体/当前进度时，模型和脚本均按以下顺序保留七区。只问单一问题则直接回答该问题，不强行生成全报告。

1. `**整体目标与进度**`：本期要达成什么、已可使用/已验收到哪一步、当前仍未满足什么。没有可靠总量或验收口径就不写百分比。
2. `**执行者进度**`：A/B/C 各自的具体功能、当前阶段、已交付结果及仍在做什么。没有对应材料就明确哪个角色缺什么记录及核对动作，不猜任务内容。
3. `**测试者进度**`：正在验证什么、已确认结论、尚未验证或阻塞的场景，说明是否已覆盖当前交付版本。
4. `**OCR 情况与后续**`：正在审查/已返回/失败/未开始及其影响；下一次检查、裁决或补审所需条件。审查结果收到不等于已批准。
5. `**强审查情况**`：是否需要、是否已开始或返回、目前结论及后续动作；影响接续时写授权有效性、截止时间或限额等待。授权、调用计数、真实用量仍保留在账本/详情，默认不倾倒工程字段。
6. `**风险与阻塞**`：具体影响、责任角色和解除条件；来源冲突在此指出差异，不能把未知包装成无风险。
7. `**下一步**`：按先后列近期可执行动作和责任角色，写清真正需要用户决定的事项。

没有新增事实的分区可写“截至观测时刻，仍在等待……”，但仅在用户询问或原定报告时点输出。纯等待的普通巡检仍静默。

## 执行者和测试者的简短分区

只报告自身范围，可按 `**结论**`、`**最新变化**`、`**开发状态**`或`**验证状态**`、`**阻塞**`、`**下一步**`组织短条目；无需套用协调者七区。单一事件可更短。发送前核对：功能名明确、每条只讲一件事、没有照抄内部摘要、当前状态已核实；这只调整正文表达，不改写证据或改变通知规则。

下面仅为表达示例，不是实际进展：

**结论**

- **文件查询功能验证通过，仍需完成代码审查才能批准合入。**

**最新变化**

- 已确认查询结果和文件获取地址一致。

**验证状态**

- 独立验证已覆盖本次交付；其他功能仍待联合验收。

**阻塞**

- 代码审查尚未完成，由协调者安排。

**下一步**

- 收到固定集成版本后，验证多个功能组合使用的结果。

## 时段总结的补充呈现

- 先写统计起止时间，再按角色分区；每个角色下分别写任务/阶段时间段、交付与当前工作、LLM 响应时间、任务排队、真实空闲、未知与补采、下一步。08:00汇总覆盖全部五个运行角色，时间段多时附完整明细。
- “角色阶段”描述开发、自测、独立验证、等待审查、阻塞等业务状态；“LLM 响应时间”说明实际请求至响应结束的客户端耗时与采集范围，不把整个阶段算成模型计算。
- “任务排队”只统计有入队与开始处理证据的等待；当前未开始的列“截至观测仍排队”。客户端 API 耗时可能包含网络、服务排队和生成，缺服务端证据时不得称“纯服务端排队”。
- “真实空闲”须已核实无可执行派单、无在途 owner/操作；等待审查、阻塞、未知均不算空闲。字段缺数据时说明原因及补采动作，如“本时段未采集请求起止；后续记录原生请求开始/结束时间”，不能只有“记录不足”。
- 分项可能重叠，阶段占用与 LLM 响应不是可直接相加的工时。状态采样为观察估算，保留粒度和缺口；不倒填历史。

## 时间与通知边界

- 用户可见时间统一 `YYYY-MM-DD HH:MM +08:00`，绑定真实来源；内部 ISO 保留原精度。优先写“发生”，仅有观测/补录时间则标明类型。发生未知明确写未知，不用 `10:2x`、“今晨”、文件 mtime 或回执发送时间冒充。
- 可靠的历史分钟时间直接保留，不因缺秒标未知、不补造秒。报告刷新不制造新成果，不把新读取时间覆盖旧业务发生时间。
- 原报告时点保持，所有固定报告继续 `no_agent`，不新增模型汇报定时请求。21:00–08:00主动通知静默，工作及落盘继续，用户主动问答走原生模型会话并正常答复。
- 白天有意义的新完成、交付、失败、阻塞变化、返修、实质问题或用户决策，先落唯一事件，再通知一次。正常心跳、持续在途、自写回声、纯等待和重复进展，普通巡检 final 仅 `[SILENT]`。
