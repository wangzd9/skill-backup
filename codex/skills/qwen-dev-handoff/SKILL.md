# 面向千问开发的需求与交接

## 目标与分工

Codex 负责需求澄清、事实调查、关键技术决策、风险验证和可执行文档；本地千问负责边界明确的实现、测试和常规返修。复杂判断或设计假设失效时升级给 Codex。让文档减少实现者的猜测，而不是仅生成篇幅完整的 PRD。

默认中文。沿用用户已经确定的目标、预算、范围与批准，不重复询问。文档任务不自动授权业务改码、付费调用、生产操作或消息发送。不要把某个项目的 Wuzu、固定预算、路径或提交审批方式推广为所有项目默认值。

## 执行流程

### 1. 恢复目标和事实

- 读取目标目录的项目规则、现有需求/交接、相关代码与测试、Git 状态；用户指定的文档位置优先，不另建一套重复任务系统。
- 用简短进度说明目标、非范围和重要假设。区分用户已决定、代码/运行验证、历史记录、设计建议、待验证事项。
- 先做聚焦搜索，再读必要片段；不要反复整库扫描或加载全部历史记录。不要把旧服务状态、测试数量、配置文件内容当作当前真实运行证据。
- 需求含截图、日志、附件或链接时核查是否真正可读并建立来源引用。占位符或路径不能替代内容。缺失材料先尝试范围内恢复，决定实现方向的材料无法获取才询问。

### 2. 澄清真正影响实现的决定

- 明确使用者、触发条件、预期结果、现状差距、非目标、约束与完成定义。
- 能从代码/文档/只读验证确定的问题自行调查。对确实涉及业务取舍、权限扩展或互斥目标的问题，集中询问必要信息；等待时继续不依赖答案的工作。
- 常规技术选择给出推荐及理由即可，不为每个模块或文档要求例行批准。
- 未解决的关键问题写入决策表，标明影响任务和所需证据；这些任务不得标为可执行。独立且已明确的任务仍可交接。

### 3. 在承诺方案前验证高风险假设

- 检查真实接口、版本、数据结构、调用链与现有可复用组件。第三方工具能力、模型视觉/工具能力、权限、恢复和生产边界需要证据，不凭名称或配置字段推断。
- 必要时做最小、可逆、已授权的验证；记录环境、命令、结果与限制。不能用大量无关测试代替关键可行性证明。
- 没有验证条件时明确阻塞项或先安排探索任务；不要编造接口、目录、运行结果和测试命令。
- 需求澄清不等于所有难点都已消除：实现中仍可发现新事实，设计和任务必须可修订。

### 4. 产出相互一致的开发文档包

编写前阅读 [文档包与任务模板](references/document-pack.md)。按任务规模合并或拆分，避免重复正文：

1. **PRD**：用户旅程、需求编号、范围、失败体验、验收条件、授权边界。
2. **技术设计**：当前与目标结构、模块职责、接口/数据/状态契约、恢复与幂等、权限、验证策略、迁移/回滚及关键决定。
3. **TODO/任务单**：稳定任务编号、依赖与可执行状态、必要输入、修改范围、输出、验收与命令、失败升级条件。
4. **执行交接入口**：千问从哪读、下一项是什么、怎样领取和返回结果、怎样验证、何时暂停/升级；引用前三者，不再复制一份。

优先复用现有 PRD、TODO 和交接入口。没有约定时建议 `docs/<feature>/PRD.md`、`DESIGN.md`、`TODO.md`、`HANDOFF.md`；小需求可合为一个文档。不要机械创建四个空文件。

用稳定的需求/验收/任务编号建立对应关系。任务围绕一个可验证产物拆分，允许含成功与失败路径；不要拆成脱离行为的“先建所有表、再写所有接口”。接口提供方先行，依赖图无环。跨文件数量由职责决定，不设任意硬上限。

### 5. 面向本地模型约束执行成本

- 每个任务给出最小阅读集：文档章节、相关文件/符号、必要现场证据和基线 revision。无需重读完整 PRD 和整个仓库。
- 明确本地千问通过什么受控执行器读写文件、应用补丁和执行测试。若只有聊天接口，则它只能提出补丁，另由已授权执行器应用验证；不能写成已经具备自动改码能力。
- 低风险、接口明确、可确定性验收的任务优先本地；跨模块设计、权限/数据一致性、反复定位失败等可升级。路由说明依据，不仅写“复杂/简单”。
- 优先用测试、类型检查、diff、契约验证判断结果；避免 Codex 逐行重做千问已经完成的简单工作。
- 返修限额使用项目约定；无约定时提出可配置建议，并标为建议。不能因模型失败而删除测试、放宽门禁或无限重试。
- 如用户要求实际试运行，可挑一个独立小任务验证交接质量；否则文档校验不冒充千问已实现或真实链路已跑通。

### 6. 交接前审查

从一个没有聊天历史的实现者视角检查：

- 能否定位所有输入并知道下一项可执行任务？
- 是否还需要自行决定关键接口、权限或业务含义？若需要，补设计或标阻塞。
- 每个需求是否有验收，每个任务是否服务需求，依赖是否闭合？
- 失败、重试、无结果、纯只读任务和中断是否有适用的处理要求？不强迫调查任务制造 Git diff。
- 命令、文件、环境和证据是否真实，计划新增者是否明确标注？
- 审查独立于开发自评；批准绑定具体产物和动作，遵循当前项目授权。
- 代码/关键需求变化会使哪些测试、审查和批准失效，是否明确？
- 是否存在相互矛盾的旧文档、遗漏的范围或把假设写成事实？

完成文件结构、链接、编号、依赖和范围检查。对未运行的验证写“未执行”及原因，不借用历史通过记录。文档变更不必跑无关完整代码测试。

## 停止与升级

关键业务决定缺失、必要现场无法取得、核心技术假设未验证时，只阻塞受影响任务；完成其余文档并明确下一步。需要新增权限或付费时遵循现有授权，不把“生成文档”扩展为运行生产任务。

千问遇到设计冲突、接口不存在、关键证据矛盾、超出预算/权限或超过返修限额时，提交升级包：任务编号、基线/上下文版本、复现、已尝试动作、相关最小 diff/日志、未确定点。禁止发送全部历史替代聚焦证据，也不要求泄露模型内部思维。

## 最终交付格式

给出文档链接、当前就绪范围、关键决定、阻塞项和下一可执行任务。明确“文档已就绪”与“实现/端到端已验证”的区别。用户应能直接把交接入口交给千问，不需要再口头解释一遍任务。
