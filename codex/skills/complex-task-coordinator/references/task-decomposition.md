# 运行时任务拆分与补位

在巡检、交付接受或执行者空闲时使用。规划者负责本期架构和关键契约；协调者可在已授权阶段、原REQ/AC和已接受契约内细化任务，不需要为正常拆分反复请用户批准，也不参与业务实现。

## 何时拆，拆到什么程度

- 先检查已有可派叶任务；任务过粗使空闲执行者无法接续时，主动检查剩余工作能否独立开发、交付和验证。最多三名开发执行者，按实际可接人数和工作独立性分配，不按人数机械切成同样数量。
- 子任务应形成可验收产物，且硬依赖的输入已接受。仅有多个worktree不表示可并行：同文件写入、迁移顺序、共享GPU/环境及未定接口保留串行，或明确公共接线owner后等待其接受。已冻结接口可以供并行实现使用；替身验证不算真实集成通过。
- 拆分只重排原范围。新需求、阶段启动、核心契约或架构变化按原规则升级；DEFERRED/WAITING_AUTH不能借拆分激活。已完成部分直接复用证据，不重新派完整实现。

## 先落文档，再派单

1. 保留父ID与历史，新增稳定子ID（沿用项目编号，如TASK-xxA/B）。父任务转为聚合，在TODO注明全部子任务、原AC覆盖和综合验收；父子不能同时领取同一实现。子任务全接受且必要集成验证完成才允许父任务DONE。
2. 每张子任务卡记录原REQ/AC、允许修改范围/非目标、固定base和契约版本、依赖、owner、产物、验证与证据、停止条件、ACK/回执路径。原AC覆盖完整且不提高完成标准；分支仍由各执行者自行创建。
3. 在短协调写锁内重读TODO与角色占用，更新任务卡、TODO父子/依赖/接续、HANDOFF及拆分事件，再派输入齐全且无冲突的子任务；协调者汇总TIMELINE和开发日志。一个子产物接受后立即重算接续，不等整波。
4. 已ACK、RUNNING、返修或等待审查的任务，不直接换owner或拆走工作。先核实当前执行者、分支、在途进程和安全检查点，记录已完成部分及剩余范围；取得交接确认后明确旧派单终止/替代边界再派子任务，不重置历史、不重复启动。

## 汇报与门禁

拆分、派单与交接是可见事件，落盘后立即通报。二十分钟报告说明实际角色占用；有空槽却不能并行时写出具体任务/文件/资源/依赖及下一解除动作，不只写“等待”。报告回合保持只读，拆分在调度回合执行。

测试者保持独立测试槽。拆分不增加按子任务付费审查的要求：依共同不变量和调用链合批、复用有效证据，适用的测试、串行OCR及强审查门禁保持。原AC满足即收口，不再拆出额外改进任务。
