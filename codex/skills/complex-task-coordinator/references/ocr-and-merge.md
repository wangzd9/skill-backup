# 协调者串行 OCR 与分支验收

本机协调者执行入口以[固定OCR流程](ocr-runtime.md)为准：`ocr_runtime.py prepare → start → status`，禁止临时runner、terminal后台及nohup/setsid。本文保留工具语义与验收依据；其中泛用拆批/恢复建议不能替代固化入口。

此处 OCR 指项目使用的代码审查能力。先读取项目规则和实际工具文档，确认可用调用方式、输入限制、超时与运行状态接口；不能把某个项目的命令、服务器或审查等级硬套到其他项目。

模型链路采用项目当前已确认的服务端点。用户要求永久切换端点后，同步调用配置、运维指引及临时runner的恢复逻辑；不能在finally中覆盖回已废弃端点。已在途进程持有旧配置时，保留任务与审查快照，安排可核验收尾，不以换链路为由降低审查覆盖或判为通过。

本文件描述协调者负责的常规弱模型 OCR，流程保持逐任务串行。强模型审查为额外机制，由用户手动触发或协调者在明确有效授权内限额调用；两者互不替代，强审查也不替代测试和协调者验收。范围见 [纠错审查](strong-review.md)，调用授权见 [授权与限额](review-authorization.md)。

## 1. 分支由执行者创建，主分支由协调者集成

1. 协调者在 HANDOFF 核实并记录实际主分支及基线，如 main 或 master，而非依据名称猜测。每个派单引用准确 base。
2. 执行者领取代码任务后自行新建本任务专属分支，优先建立隔离 worktree；可采用 `feature/<专项>/<TASK>-<owner>` 一类名称。检查已有分支、用户改动和工作区，不能覆盖或 reset 既有工作。
3. 开发执行者把实际分支、工作区和 base 写入状态/回执，完成改动范围内的快速单元测试和开发者自检；交付提供固定 commit 和真实 diff。返修的新 attempt 可延续该任务分支，新任务则从协调者指定的最新基线新建分支。独立测试者负责验收计划中的集成测试、回归和证据采集，两者不能相互替代。
4. 执行者不得直接修改、合并到主分支，也不在提交审查后偷偷改变交付快照。协调者基于明确 base/head 验收，不能审查移动中的分支名后默认结果覆盖最新提交。
5. 协调者核对测试者提交的验收证据、OCR 门禁及集成条件，并确认该快照不需要额外强审查或强审查门禁已解除后，才合入主分支，记录合入提交并标 DONE。合并改变产物时向测试者派发受影响范围的合入后验证；合并冲突回派指定开发 owner 或明确协调者的接线所有权，不能由协调者顺手代写业务修复。

本工作流的实现授权不自动包含推送、生产部署或其他外部写入。已有相应授权则继续，不重复询问。没有 Git 的项目明确说明不能执行分支步骤，不能虚报合入。

## 2. OCR 只有一个发起者、一个在途批次

- OCR 由协调者统一排队、触发、读取和裁决；A/B/C 与测试者都不运行 OCR。开发执行者冻结交付快照后可释放开发槽，承接无冲突的新任务；核实出问题后以新 attempt 召回原 owner。测试者可以并行执行已派发且不受 OCR 结果影响的验证。
- 三路开发可以继续并行，但同一专项同时最多一个 OCR 批次在运行。共享审查服务另有全局串行限制时，遵守其既有队列/租约。
- 在 TODO 任务卡记录审查队列/结果，HANDOFF 记录当前 `task/attempt/batch/base/head/run_id/process/status`。详细覆盖清单和结果放协调者管理的 `reviews/TASK-xxx/attempt-n/`，不另建任务调度平台。
- 先写批次和固定快照，再触发；工具自动产生的结果由协调者管理。调用失败、未配置、空输出或超时都不等于“无问题”。
- 每次轮询确认上一批已完成、取消或退出后才触发下一批。超时仅表示结果未取得时，不可假设旧任务已停止并立刻重复启动；恢复会话也先核对在途运行。

## 3. 审查前先拆输入并记录覆盖

针对固定 `base..head` 建立差异清单，核实修改文件、变更行、输入字节/预估上下文和相关依赖。按实际工具能力选择文件过滤、代码范围或只读审查材料；没有验证支持的参数不直接提供看似可运行的命令。

拆批原则：

1. 先用小而相关的一批确认时延和实际输入限额，留足提示、上下文和输出预算。文件个数、行数只是参考，不能把模型最大上下文当作安全批次大小。
2. 普通文件按相关模块归组；大文件按完整函数、类或职责区间拆批，保留必要 import、类型、调用方、数据约束和错误路径。不能只截取零散变更行或把函数截断。
3. 同一文件的多个片段分别记录原文件、符号/行范围和上下文。工具不支持范围、但已核实支持自定义材料时，准备只读输入，带源路径、base/head、差异与完整相关符号；不得通过修改业务文件来缩短审查输入。
4. 单独安排跨文件/跨片段契约批次，覆盖调用与返回、状态流、迁移/模型一致性等实际风险。局部全部通过不代表集成契约已经审查。
5. 明确生成物、第三方代码或其他不适用文件的排除依据；不能因为文件太大或耗时就静默漏审。
6. 起跑前必做尺寸预检：固定 base/head，用实际 `--preview` 核对入选/排除，统计 diff 与完整相关符号、规则、背景、规划和依赖输入。>500 行作为需详细预检的信号，不是工具上限；大文件独立成批仍可能过大。**当前 OpenCodeReview v1.12.13 的 `--max-tokens` 不会拆开单文件**，单文件直接成一组，多文件超限最多拆到逐文件。不能把调小参数或 selected=1 记为已按职责拆分。起跑前记录可测输入/估计方法和保留工具结果的余量；初始提示或冻结消息已接近压缩线时，先调整真实材料或有效预算，不盲跑。

### 3.7 当前 OCR 参数与压缩契约

以下依据 v1.12.13（fabbdb2）；2026-10-14 已升级 v1.13.0（1672852，registry 当前最新）：CLI 参数面兼容核对完成（--from/--to/--preview/--max-tokens/--effort/--concurrency/--exclude/--timeout 均在，新增 --audience/--max-tokens-budget/--max-git-procs 不影响既有用法），门禁与 fixture 同步为 v1.13.0，15 项隔离回归全绿。后续升级仍须重新核对 CLI 帮助、实际 session 与 manifest 能力后更新门禁。

| 参数/现象 | 实际含义与处置 |
|---|---|
| `--max-tokens` | 每组提示 token 上限并参与对话压缩阈值；不是单文件切分开关，也不是服务端生成长度。0 采用配置/任务模板默认，不是无限；review 模板当前默认200000，可被配置覆盖，其他模板58888不能当review默认。 |
| 压缩阈值 | 60%触发后台、80%同步压缩；20000对应12000/16000。前两条system/user保留，含diff/规则/规划；新摘要追加到原user，反复压缩可能增长，压缩后仍超线即停止。模型token、OCR估计、字符数分别记录，不能混用。 |
| `--timeout` / `OCR_LLM_TIMEOUT` | 前者每任务分钟级预算含请求与重试；后者独立单请求秒级超时。增超时只针对经证据确认的超时，不能消除压缩停止。 |
| `--max-tokens-budget` | 整轮累计input+output预算，独立于max-tokens；部分文件失败时可能退出0，仍要读manifest。 |
| `--effort low` / `round 1/2` | low把配置总review轮数降为1，不缩输入/压缩压力；1/2是当前第1轮/总2轮，首轮停止不表示已经耗尽2轮。 |
| `--resume` | 复用身份匹配的已完成文件覆盖，失败文件重新派发；不是从失败工具调用/压缩点续跑。先确认旧进程已结束，核对模式、base/head、选集、规则和运行配置；identity拒绝后先查差异，不重复撞门。 |

工具没有已验证的单文件范围参数时，先用完整职责材料定位能力缺口；不得改业务文件凑小diff、漏审或伪称原OCR通过。已验证的 `ocr delegate rule --from <base> --to <head> --format json <path>` 可只读导出解析规则（不调用模型），**不接受函数/行范围、不执行审查**。宿主/强模型代审必须另记身份与结果，不能自动替代弱OCR门禁。若需改工具或门禁，由当前授权及项目规则决定。

审查背景写清当前任务不变量、允许行为及非本次范围。可提醒模型复用已取证结果，只有证据不足/冲突才重读；围绕当前变更提交可定位findings或说明未完成覆盖，不将未变依赖的风格偏好扩成任务。背景和low只是辅助，不能冒充对压缩根因的修复。

工具既不支持范围也不支持自定义材料时，不虚构参数或声称完成片段 OCR。记录能力缺口，采用实际支持的较小文件批次/配置；仍无法覆盖的大文件保持待验收，协调者决定范围内的适配或解除条件。

每批最少记录：

| 字段 | 内容 |
|---|---|
| batch_id / task / attempt | 批次身份与所属交付 |
| base / head | 固定审查快照 |
| inputs / covered_scope | 源文件、符号/范围、关联上下文及审查材料路径 |
| exclusions / remaining_scope | 排除原因与尚未覆盖内容 |
| run_id / process / timestamps | 真实运行定位、开始/结束和时区 |
| status / result_path | QUEUED、RUNNING、COMPLETED、TIMEOUT、FAILED 或 CANCELLED；真实输出 |
| findings / verified_decision | 问题与核实结论；不能把未执行写成零问题 |

## 4. 超时与结果处理

使用可返回的执行/轮询方式，让协调者仍能按 HANDOFF 间隔处理 ACK、阻塞和进度。避免一次等待整批长任务而使其他会话失去协调。

超时先记录已有输出、未覆盖范围及旧进程状态；确认旧运行停止后，把失败批次进一步按职责拆小，或在工具允许范围内调整输入/超时。只重做未取得有效结果的范围。无项目约定时，同批同因两次失败后升级说明，不无限重试或无限加长超时。

长 OCR（>15 分钟）的进度监控与中断恢复（2026-10-10 r6 教训，两处都踩过）：

1. **监控实际 session 事件与进程身份，不以 stdout 为准**：stdout 重定向到 log 是缓冲的，收口才 flush——0 字节 log 不等于没干活，拿它当“卡死”证据会做出错误干预。ocr 起跑即把 session 实时写盘（如 `~/.opencodereview/sessions/<workspace>/<uuid>.jsonl`，也可从进程 fd 指向确认）；mtime/事件增长只能证明日志活动，不能证明有语义进展或已覆盖；辅以PID/start identity及服务端请求证据。
2. **中断恢复先查 session uuid、manifest 覆盖及进程身份**：有session不表示能从失败点续跑；不能对同一在途任务重复resume。仅已完成且身份匹配的文件可复用，失败文件仍重审。stdout空也可能有session；先保留有效发现和覆盖证据，确认旧任务退出后才选择恢复或新材料。
3. **给每个长批设硬截止并提前告知用户**：起跑时记下预计收口窗（参照同规模批次实测时长 × 并发负载系数），到点先查实际事件、进程身份及覆盖再裁决续等/停止后恢复；负载变化（其他 worker 抢同一 LLM 卡）要显式记进预计窗修正，不要只说“还在跑”。

协调者对结果核实：真实问题回派开发 owner，需运行证明的疑点派给测试者，误报注明代码/运行依据，未判定问题保持待处理。问题等级和通过标准遵循项目实际门禁，不另创一套质量阈值。

返修变更产生新 head，使旧审查不再自动覆盖新产物。重新审查受影响批次及必要关联契约；仅在输入、依赖和验收前提确实未变时复用其余结果，并记录依据。

只有弱模型 OCR 清单覆盖完整、有效结果符合门禁、必要验证通过、适用的强模型门禁已解除且实际合入主分支，Git 代码任务才能 DONE。串行 OCR 的排队、拆批和等待不能降低验收标准。


## 5. 失败先诊断，再决定下一次调用

只读诊断（任意目录，零模型调用；返回0只表示诊断读完，不表示OCR通过）：

```bash
python3 /home/wang/.codex/skills/complex-task-coordinator/scripts/ocr_session_status.py /absolute/path/session.jsonl
```

可一次给多个session，输出终态、固定范围、selected/completed/reused/failed/waived、未覆盖路径、manifest终因、LLM错误、重复工具调用和字符/usage统计；脚本不请求模型、不重试、不改配置，也不裁决合入。没有session_end、未知schema、截断日志或无manifest时保持未收口并核对进程；不可用files_reviewed、0 comments或退出0代替实际完成覆盖。`coverage_complete=true`只说明本session文件身份完整，仍需核对整个批次及跨文件契约、findings裁决和测试。

- manifest明确 `context compression exceeded its threshold`：按§3.7调整真实输入与有效上下文；不以直连/超时/low/resume反复尝试相同材料。
- manifest明确deadline/timeout：区分任务截止与单请求超时，结合同时段请求/服务端/进程证据；不能直接归为网络或排队。
- `context canceled`、`main_task did not complete ... round 1/2`：属于症状，优先读manifest；后台压缩可能主动取消请求。只有进程信号/回合回收等独立证据才定为宿主杀进程，只有对应网络/服务端证据才定为传输失败。
- 失败session的planning/压缩摘要仅是待核实线索，不是completed覆盖；先逐条核代码/运行证据，再决定复用。same cause两次失败后停止原样换参循环，保留有效结果、未覆盖范围与下一步实质变化；已有在途调用先观察，不重复启动。

证据实例：[TASK-16B八轮诊断](/home/wang/work/doc/analysis/t16b-ocr-failures-20261013/REPORT.md)。可重复的工具/规则问题先纠正，弱模型重复取证是放大因素；没有相同输入对照不量化归因，不把一个大文件失败泛化为整个模型不能审查。此经验不新增模型调用、强审查或部署授权。


## Hermes 锁与返回周期

群聊/定时具有同一协调权限，均走同一项目单写租约；不保留机械化身权限限制。长 OCR 独立持有稳定 inode 的 ocr.lock，不覆盖协调者文档锁。检查工具实际结束后继续，不能删除锁文件来解锁，文件存在也不表示 flock 被持有。等待不阻止下一轮调度。合入前完成适用 OCR 门禁，禁止以“先合后审”作为自动例外。

**OCR发起方与寿命**：当前已验证的跨回合方式是ocr_runtime.py通过用户systemd管理器创建独立.service，PID/cgroup不得属于hermes-worker-cron的scope。terminal后台、nohup/setsid及主会话是否持久不能仅凭启动后ps存活证明；旧链保持观察，未来只调用固化入口，不重新尝试脱管命令。没有systemd用户管理器或配置错配时BLOCKED，不退回临时脚本。

脚本全链持有global及project稳定锁，记录服务、PID/start ticks、固定commit、session、日志与终因；status可短时返回，原poll继续调度。直接CLI仅由脚本用于preview/规则导出/内部审查，低max-tokens不拆单文件。实际测试与独立审查各沿用原门禁；0入选核排除依据，不能写已审。完整命令、默认参数、重复阻断与限额补审见[固定流程](ocr-runtime.md)。
