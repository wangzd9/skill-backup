# 夜间静默、当前事实与分时段总结（quiet-digest-v2）

## 原报告时点与通知边界

按北京时间 Asia/Shanghai 运行，保持现有时点：

| 角色 | 主动定时群报 |
|---|---|
| 协调者 | 08:00统一夜间汇总；白天08:20–20:40每20分钟当前进展报告 |
| 执行者A/B/C、测试者 | 11:00、15:00、18:00各一次时段总结；旧20分钟与2小时空闲报告保持停用 |
| 所有运行角色 | 21:00（含）–次日08:00（不含）不主动定时汇报或事件通知 |

夜间开发、五分钟脚本巡检、必要模型接续、自测、独立测试、派单、OCR及有效授权内的强审查继续，文档、检查点与事件照常落盘；只抑制主动通知。原锁、身份、分支、授权和全部门禁保留。

白天普通巡检发现有意义的新完成、交付、失败、阻塞变化、返修、实质问题或需用户决策时，先落带稳定 event_id 的事实与证据，再即时通知一条，同一事件不重复报。只有心跳续租、持续在途、纯等待、自产回声或重复进展时，非总结 poll 的 final 必须仅 `[SILENT]`。协调者原有派单、批准、合入通知继续遵守相同去重与静默规则。

夜间 cron final 仅 `[SILENT]`，脚本报告空输出，不用 `send_message` 绕过；Hermes投递层按实际发送时刻抑制，晚于21点结束的白天回合亦然，保留本地结果并记 suppressed。cron final 由原群自动投递，不自行双发。其他安装需核实投递扩展实际部署情况，不能凭模板声称生效。

人工自然语言问答、进度、解释与方向讨论保留 Hermes 原生模型会话，不自动入业务队列、不等五分钟巡检；夜间用户主动问话正常答复。只有明确业务动作才按既有请求记录、共同租约、授权与门禁执行。后台 HANDLED 不能冒充业务完成或用户收到答复。

## 五分钟文档检查与业务接续

协调者派单后，各角色每五分钟由独立脚本检查自己相关文档、实质输入及 owner 身份，不靠模型轮询，也不靠文件 mtime 判断业务变化。有任务或实质变化先持久入队，角色空闲才唤醒模型；同角色忙时继续排队，当前工作结束后接续，角色通过文档交互。

无变化、无未处理输入时不启动模型；正常观察刷新不制造 session/event 回声。已运行模型在安全检查点检查新输入，处理后才确认对应指纹；旧 ack 不能吞新输入。五分钟是检查周期，原生队列延迟和在途工作如实记录，不能承诺五分钟完成接单。详见[脚本巡检](script-observer.md)。

## 角色报告契约与事实范围

人工问进度、普通poll的有意义事件、脚本当前报告和时段汇总共用一个报告契约。先按绑定项目及角色取得本轮报告材料：

```text
python3 绑定的runtime_tools.py report-input --project ROOT --role ROLE
```

`ROLE`使用当前绑定的COORDINATOR、A、B、C或TESTER；命令默认返回JSON，无需`--json`。读取其中`sections`与同源的`markdown`基稿，证据按`evidence_reference`定位；模型解释仍限于相同事实范围。角色材料只包含本职责及必要依赖，不能拿全项目摘要代替。首次恢复需查原任务材料，报告时仍以本轮角色契约为入口；长操作结束、最终汇报前刷新一次。非进度单问题只读相关证据直接答题。

- 协调者覆盖整体目标、A/B/C和测试者、OCR、强审、风险和接续；任何进度入口都按显示Skill完整七区。执行者/测试者只报告本人当前工作、完成结果、阻塞依赖和下一步，不写其他角色完整状态或全局审查账本。
- 同一角色的当前执行、已交付等待、其他在途责任分别说明。分配到多个任务不等于同时开发，旧批次只读观察不能覆盖当前开发任务；没有足够证据确定实际阶段就明确待核对。
- 当前障碍须有适用任务、版本、状态和解除条件。明确解除的历史障碍不再作为当前阻塞，原失败与后续补审保留各自身份。证据不足或冲突时保留具体不确定性，不能按段落关键词或最新mtime决定门禁。
- TODO负责业务任务状态；固定快照测试回执负责已验证行为及版本；OCR运行和裁决、功能接受、合入、生产各负其责。任务表未同步不抹去已有验证，也不自动批准合入。旧验证与新交付不同须核对差异及可复用范围。
- 每项保留来源定位及可信的发生、观测、补录时间。报告契约是当次权威文档的可重建视图，不是另一份任务状态；刷新时间不能冒充业务发生时间，读取失败不得以旧聊天印象填当前结果。
- 需要核对具体风险或版本时按契约的来源取证，必要时读取完整 `runtime_tools.py progress-facts --project ROOT --json`。完整证据和身份保留原样，不能为群报改写源数据；不默认给执行者/测试者注入全局包或历史全文。

显示结构和简短条目只由[显示Skill](../../feishu-progress-style/SKILL.md)维护，模型和脚本按相同契约呈现，不用正文替换器修正事实。显式`/progress`可无模型生成进度；自然语言保留原生模型答复。固定报告仍`no_agent=true`，不增加报告模型请求，也不改变已有测试、审查、授权和合入门禁。

## 时间与来源

- 内部写入时间为系统生成的带时区 ISO 8601，分开有证据的发生、实际采集和补录时间。仅有观测写“截至该时刻已观测到”，不声称就是发生时间。
- 面向用户统一 `YYYY-MM-DD HH:MM +08:00`，标题为实际生成时刻；进度旁标发生、观测或补录。可靠历史分钟时间直接保留，不因缺秒标未知、不补造秒。
- 发生未知明确写未知；旧 `10:2x`、`10:1x`、“今晨”只保留历史原文，不扩成可靠时刻。文件 mtime、进程启动、cron起止、租约获取、消息/回执发送均不自动成为业务发生时间。
- 当前事实读取不等于实时生产探测；新的无变化观测不能覆盖业务事件发生时间，也不能当新成果再次通知。

## 时段范围

- 08:00夜间汇总：前日21:00–当日08:00，覆盖协调者、A、B、C、测试者；前日18:00–21:00记录附同一总结补充明细。
- 11:00个人总结：当日08:00–11:00；15:00：11:00–15:00；18:00：15:00–18:00。有任务和无任务均生成，不为总结调用模型。
- 完整段落、事件与来源保存 `inbox/control/runtime/digests/日期/ROLE-kind-HHMM.json`，原始观察保存 `runtime/activity/日期/ROLE.jsonl`；它们可重建，不替代TODO或验收决定。

## 时段报告的四类时间与缺口

`activity_report.py`从真实事件、文档事实与原生运行记录重建报告。用户可见正文按角色加粗分区，分别列下列信息，不能把它们混为一个“占用”时长：

- **角色阶段**：列任务、功能、开发/自测/独立验证/等待审查/阻塞等阶段的起止与观察估算时长，以及交付和当前工作。阶段占用不是模型计算或精确人工工时。
- **LLM响应时间**：列有原生请求起止证据的客户端请求至响应完成耗时、请求数/覆盖范围及来源。客户端 API 耗时可能包含网络、服务排队和生成，不能叫“纯服务端排队”；只有服务端排队证据才单独呈现该项。
- **任务排队**：列有入队与实际开始处理证据的等待时间、任务与原因；未开始的说明“截至观测仍排队”。角色忙导致的业务队列与模型 API 耗时分别统计，不能混成同一队列。
- **真实空闲**：仅核实无可执行派单、无在途 owner/操作的观察区间才计入。等待审查/验收、阻塞、未知、采集缺口均不算空闲；任务可派而未接续不能记空闲。

四项可以重叠，不能相加成总工时。状态采样通常约五分钟，超过十分钟未采集的缺口标未知；来源若有更精确可靠的起止证据可以使用，但要说明类型和范围。

每项未知都须给具体原因与补采动作，例如“本时段原生日志缺少请求结束事件；核对原生会话记录，后续采集request-start/request-end”，或“入队时间缺失，无法计算历史队列；以后保存首次入队与开始处理时间”。不只写“记录不足”，不把未知当零，不倒填上线前或服务停机期间的历史。没有服务端分解证据时明确当前只能取得客户端响应耗时，服务端排队无法单独量化。

## 配置与维护

本机策略文件 `~/.hermes/role-reporting-policy.json`；沿用原 poll/report/morning job ID、角色群、origin/deliver、错峰、当前启停状态和在途任务。个人report为`0 11,15,18 * * *`；协调者progress为`0,20,40 8-20 * * *`，08:00槽脚本静默让位独立morning `0 8 * * *`。旧idle-report暂停保留历史，不恢复旧两小时规则。

定时角色回合只消费既有配置，不自行创建/修改cron；新项目模板保留相同约定，未绑定专项不启动任务。迁移备份，不停止业务进程，不重置ACK、事件、任务状态或门禁。隔离草案只产出可审核规则和验证，不把正式配置描述为已部署。

分别记录脚本校验、原生投递抑制、真实定时运行、自然模型答复和群内送达。模拟测试不能称已观察整夜，脚本通过不能称业务验收完成；服务停机、队列延迟及事实包缺口如实报告。
