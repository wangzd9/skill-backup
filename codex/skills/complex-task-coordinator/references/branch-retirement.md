# 合入后的分支与 worktree 收尾

在任务合入并完成适用的合入后验证、需求最终交付结束或用户要求盘点历史分支时读取。协调者负责清理台账与执行结果；执行者和测试者负责释放自己使用的工作区及进程。业务验收状态与清理状态分别记录，不为清理重开已验收业务任务。

## 判断哪些还要保留

| 对象 | 处理 |
|---|---|
| 当前工作分支、主干、明确长期维护/发布分支 | 保留 |
| 当前或暂停需求绑定的 workflow / integration 分支、下游任务基线 | 保留到需求及引用释放；不能仅凭已进 main 删除 |
| 未被指定目标包含的提交、返修/审查/验证仍使用的快照 | 保留并列出具体差异或责任人 |
| 备份、回滚、审计保留对象 | 核对保留目的及期限；无期限时交 owner 明确，不能按年龄推断可删 |
| 已合入且所有引用和工作区均可释放的短期任务分支 | 纳入清理 |

分支名字、提交时间、任务 DONE、无 upstream 或 `[gone]` 均不是合入证明。固定 source/target 的完整 SHA，用 `git merge-base --is-ancestor SOURCE_SHA TARGET_SHA` 核实提交可达性；目标必须是实际授权的集成分支，不默认 main。squash/cherry-pick/rebase 后 ancestry 不成立时，`git cherry` 只能辅助辨认等价补丁，仍需核对合入回执、最终差异及保留用途；不据此自动强删。

## 合入后的收尾顺序

1. 记录 repo、run/task/attempt、source branch/head、target branch/head、合入方式与结果 SHA、适用验证及审查回执。fast-forward 可无独立 merge commit，记录实际结果即可。既有交付必须推送时，核实交付完成；清理不能替代发布门禁。
2. 逐个核实派单、基线引用、角色 execution、工具子进程、测试、OCR/强审查及未完最终交付是否仍需要该分支或 worktree。租约过期或 PID 查不到不单独证明可释放；按原生身份核实 writer 退出。暂停需求也可能仍有引用。
3. 开发/测试 owner 保存有用成果和工作区外的验证证据，给出精确 worktree/head 与可释放依据。`git worktree list --porcelain` 找出全部占用者；检查 staged、unstaged、untracked、ignored、嵌套仓库/子模块、锁与仍在使用的目录。干净 Git 状态不证明 ignored 的证据或缓存可以丢弃。不要把 `.venv`、scratch 或未知文件直接归为垃圾。
4. 协调者在已有清理授权内冻结待删清单、确认非保留对象，并在实际执行前重新核对 source/target SHA、引用、进程和目录内容。身份或内容发生变化则重新评估；未知 owner、dirty、必要证据尚未外置或活跃/未知进程均保留，不强杀或清空工作区。
5. 已具备清理权限的维护入口先移除可释放的 worktree，再以 `git branch -d -- BRANCH` 删除本地短期分支。`-d` 的 upstream 判断不能代替步骤1的指定目标证明；执行失败保留并记录原因，不自动改 `-D`。不使用 `rm -rf`、`git clean`、强制 worktree remove 或批量 prune 处理未知对象。等价补丁需特殊处置的，另记已核验方案与对应授权。
6. 有远端删分支授权时，另行核对准确 remote URL、远端 source SHA、保护规则和协作者引用；按预期 SHA 做带 lease 的精确删除，拒绝移动后的远端分支。普通 push 或本地清理授权不包含远端删除。远端删除后核实 `ls-remote`，再清理对应失效 tracking ref；tracking ref 不是服务器分支。
7. 回读 refs/worktree 列表，并记录每个对象的 `PENDING / RETAINED / CLEANED`、原因、owner、精确 SHA、执行及核验结果。它们仅是清理条目状态，不替代业务 checkpoint 枚举。部分成功逐项记账，重试先对账；保留回执、审查、开发日志、事件和必要 Git 对象的持久引用/备份，不能依赖 reflog 永久可恢复。

## 各模式的执行边界

- **ACTIVE：** 仍只使用原生专用工具。当前安装的运行时没有分支/worktree 清理命令；因此本规则用于盘点、owner 释放与记录待清理，不能虚构 action、通过 shell 绕过角色工具或宣称已自动执行。由获授权维护者执行具体清单；将来接入受管入口时须验证身份、并发引用、干净度、精确 SHA 和中断对账后再启用。不得因清理入口缺失阻塞无关开发或改写已验收结果。
- **LEGACY/STAGED 或直接维护会话：** 在原角色职责及用户已给的清理范围内执行。只要求盘点/讨论时输出清单，不删除；已有明确清理授权则不重复索取。同一需求的正常收尾优先处理本轮新产生的短期对象，历史积压单独形成批次。

## 输出与验证

在既有 decision / HANDOFF / development log 中记录事实并链接完整清单，不另建任务调度源。清单至少包含：对象、固定 source/target SHA、合入依据、worktree、引用/进程检查、改动与 ignored 检查、保留/清理原因、责任人及实际结果。

完成条件是每个候选都有可核验的清理结果或保留理由。仅修改 Skill、指南或添加清单，应明确写“流程已更新，自动清理接口尚未实现，分支未删除”；不能写成运行时已部署。
