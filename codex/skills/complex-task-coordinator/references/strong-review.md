# 已完成功能的强模型纠错审查

这是协调者串行弱模型 OCR 之外的额外审查。目标是核验已交付功能是否实现既定需求，以少量高价值纠正降低逻辑缺陷和返工。默认在一个约定功能批次完成开发和常规测试、形成固定代码快照后进行；不按每个任务或每个提交触发，不自动增设实现前强审查。强模型不替代测试、弱 OCR 或协调者验收。

## 1. 冻结范围，先判断是否需要审查

审查包引用既定需求/AC、契约版本、部署环境和本批交付范围，记录对应文档版本或内容哈希。审查过程中不增加功能，不抬高原有成功标准，不把后续阶段要求提前。必要数据保护可以来自既定功能直接蕴含的不变量，但必须说明它与哪项需求的关系。

协调者记录以下一种判断：

| 判断 | 条件与动作 |
|---|---|
| `NOT_REQUIRED` | 当前快照的常规验证与弱 OCR 已充分证明受审行为，没有具体未闭合风险；按原门禁继续。 |
| `MERGE_INTO_REVIEW-xx` | 已完成功能共享调用链或不变量，合批可减少重复阅读；写明目标批次和不能越过的相关门禁。 |
| `REVIEW_NOW` | 已完成交付存在具体逻辑风险或关键证据缺口；写清风险事实、待回答问题、对应既定需求/AC和受影响门禁，再准备审查包。 |

模块名称、diff大小、任务结束或阶段结束都不能单独作为触发理由。预算是费用预估，不是必须用完的审查配额；没有必要的批次不生成。已经接受且语义未变的契约不重复审。

开发中尚未明确的关键契约先由协调者按原规划流程澄清，暂停的是确实依赖该未决行为的工作，不自动启动付费审查。用户明确要求实现前契约审查时才作为例外；仍只回答约定问题，不重新设计系统。

## 2. 触发方式与允许的批次

```text
执行者交付功能和自测 → 测试者提供必要独立证据
→ 协调者核对代码、证据和弱 OCR → 判断明确审查需求并准备一份包
→ 暂停相关门禁 → 有效授权内由协调者限额调用，否则提醒用户手动触发
→ 独立结果返回 → 协调者分类问题，组织最小修复、验证或合入
```

- 执行者维护正常回执，不另建强审查材料。协调者仅在 [用户授权与限额](review-authorization.md) 满足时通过统一Codex入口调用，不自动续期或无限重试；无授权保留人工流程，结果未返回不能默认通过。
- 默认审查节点是稳定功能交付的合入前核验，以及最小链路完成后的必要跨模块核验；阶段结束时没有新增风险或证据缺口可以 `NOT_REQUIRED`。
- 按共同不变量和调用链合批，例如接收/调度、识别/切包、发布/登记。不要按三名执行者分三次，也不要为等待合批阻塞必须先接受的上游交付。
- 多分支审查使用固定集成候选或等价代码树，绑定唯一target；冲突或业务接线回派开发owner。强审查暂停相关合入或验收，不冻结独立开发和测试。
- 人工流程未触发、授权不足或额度已满时保持相关门禁等待；独立任务继续。只在实际运行或恢复时检查，不承诺固定返回时间。

## 3. 问题必须分类，不能把建议变成任务

| 分类 | 必须提供的依据 | 协调者动作 |
|---|---|---|
| `CORRECTION` | 已有需求/AC或其必要不变量、预期/实际行为、触发条件、代码/运行证据、错误后果 | 在现有任务下按问题ID派最小返修；只阻塞实际受损的门禁。 |
| `VERIFICATION_GAP` | 哪项已有AC尚未被证明、为什么现有证据不够、补齐它的最小验证 | 派测试者补必要证据；不要求新增通用测试平台或全套质量工程。 |
| `OUT_OF_SCOPE` | 新功能、未来规模、偏好式重构、泛化架构或额外质量标准 | 可简短记录建议，默认不派单、不进当前TODO、不阻塞；只有用户明确采用后才进入规划。 |

证据不足的疑点写“待验证”，不能直接当确认缺陷。无依据的“最好支持”“以后可能”“建议统一重构”不能升级为本期工作。

每个阻塞项必须给出对应需求/AC、触发与后果、证据、最小修复边界和解除条件。严重度高不免除这些要求；无法证明关联的建议不能阻塞本批。

模块审查只核验模块承诺的行为。真实模型、样本、容量或生产证据属于单独阶段时，保留其原有门禁，不把它们追加为无关模块的合入条件。模块通过也不能代替那些尚未完成的阶段。

## 4. 一份短而可核验的审查包

使用 [审查包模板](../assets/strong-review-pack.md)，至少提供：

1. review_id、审查类型/作用门禁、任务范围、实际base/target、契约版本及语义哈希、冻结的需求/AC基线。
2. 已交付行为、未闭合的具体问题、必须成立的不变量、非范围；不要让强模型继续发散需求。
3. 完整变更文件清单、关键调用链、重点代码位置及可定位完整diff；正文给关键实际代码和必要上下文，不能只有协调者解释。
4. 命令、退出码、环境、证据commit、关键断言、日志路径及未执行项。其他commit的证据必须核对到target的行为差异，否则补跑必要验证。
5. 弱OCR的确认/已修复问题、核实误报、未覆盖项和待裁决疑点。

不复制全部历史对话、四份全文设计或所有日志。材料过大按调用链拆批，不用固定行数截断；测试和成功条件的修改不能隐藏。优先复用匹配当前快照的有效证据，不为打包反复跑昂贵全量验证。

审查包准备好后记录review_id、触发原因、base/target、输入/结果路径、暂停门禁及可继续任务。有明确有效授权时自动起跑并通报grant_id/call_id/剩余额度；否则请用户手动触发。群内通知按显示Skill组织。

## 5. 纠正、增量复审和收口

- 协调者核对结果身份和快照，再按第3节分类；审查者的建议不是自动授权。返修单引用原任务、问题ID、对应AC、允许范围和解除条件，不借返修添加新功能。
- 修复允许涉及必要上下游，但必须说明它们怎样导致同一错误。优先完成该缺陷的最小闭环；需要超出既定范围的大改时单独说明并升级，不自动拆成额外工程。
- **结果处置默认规则（用户 2026-10-13 裁决，SR-16B-R1 确立）**：`PASS`=核对问题关闭/覆盖/测试证据后按原门禁接受；`REWORK`=对确认问题最小返修+增量复验，**不自动升级全量重审**；只有发现**具体的遗漏风险或证据缺口**才补审相关调用链，完整业务链路验证归独立验收门禁（如 12S-D），不由强审代跑。文件行数大不是升级全量审查的理由。
- 验证限于问题复现、修复后的关键断言和必要受影响回归。不能因审查建议自动铺开无关测试矩阵，也不能删测试、弱化断言或错误放行来省工作。
- 复审默认只看本轮问题ID、修复diff、对应证据和受影响上下文。已关闭且仍有效的问题不再开单；不重新逐行审查历史代码。新发现只有证明损坏本批既定行为时才成为纠错项，其他建议仍归非范围。
- 影响受审行为的新逻辑须核对/补审，旧commit的PASS不放行新行为；已接受且未变化的材料继续复用。
- 本轮阻塞问题经验证关闭、原有验收条件满足后即收口，不以“还可以更完善”为由继续加单。同根因两轮仍未解决则整理最小升级包交用户决定，停止无限返修。
- 合入后必要集成验证仍由测试者执行。工程闭环和生产启用分别判断；原有真实时间映射或真实切片门禁缺证据时保留等待，不能以模块通过代替。
- **多依赖接线门禁口径（用户 2026-10-13 纠正）**：上游 A 合入后下游可继续开发与准备核验（不闲置），但正式接线验收必须等全部硬依赖（如 16B+12S-A+12S-B）接受合入，不能只凭一个依赖合入宣布接线通过。排程里"~HH:MM 返回"是估计，停止点以实际证据判断。

## 6. 结果与轻量记录

强模型优先核验业务逻辑、跨模块契约、状态/事务顺序、幂等并发、异常/无命中分类、发布恢复和时间边界，并给每项问题附第3节的分类与依据。默认只审查，不修改业务代码、合并或部署；无法访问约定文件系统时输出完整结果供保存，不能声称已写文件。

结论仍为 `PASS` / `PASS_WITH_FOLLOWUPS` / `REWORK_REQUIRED` / `INSUFFICIENT_EVIDENCE`，绑定当前快照和具体门禁。`PASS_WITH_FOLLOWUPS`仅用于范围内明确非阻塞事项；非范围建议单列，不因它们降级PASS。必要证据不足不能PASS。

每批只记录实际token/费用（不可获取写未知）、确认缺陷、核实误报、后续遗漏、返修轮数和重复阅读。费用记录不新建平台，不承诺准确率。
