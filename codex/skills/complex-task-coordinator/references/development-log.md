# 协调者维护开发日志

协调者根据实际进展维护项目绑定的 `development_log`，未配置则使用共享根 `DEVELOPMENT-LOG.md`；该文件是进展摘要，TODO仍是唯一任务状态来源。

- 在重要交付、独立验证结论、审查纠错、批准合入、阻塞/解除、里程碑或授权变化时更新；相同证据/事件ID只记录一次。无变化巡检不新增日志，二十分钟报告可引用最新日志位置。
- 每条包含实际发生/记录时间、任务/attempt或review/call_id、实际分支/commit、行为变化与当前结果、验证/证据位置、遗留问题及下一责任人。只记录已经发生的事实，开发者自报与独立验证、工程闭环与生产启用分开写。
- 文档采用追加或先读后原子替换，持有短协调写锁；不截断已有日志，不把历史事实重写成新结果，不长期占锁等待审查。
- TIMELINE保留原始事件，开发日志只做有意义的阶段摘要，不复制全量时间线、所有日志或聊天；任务派发仍按TODO和decision，不从开发日志重新领取。
- 如仓库已有功能日志流程，读取并遵循其Skill/规则。开发日志随上述实质事件更新，不等正式日志批准。以rosbag-catalog的feature-changelog流程为例：功能完成且有适用验证证据后，在本轮交付收口时生成/合并pending候选并更新changelog/REVIEW.md；用户明确批准指定功能编号后才approved；随实际系统更新成功发布后才released并更新CHANGELOG.md及Web /changelog。一个完整功能可汇总多个子任务，不逐commit重复生成。缺证据派测试者补证并记录责任人；候选生成失败记录失败与恢复动作，不静默拖到发布时。
- 协调者不自行批准正式日志；“继续”、开发验收通过或自动审查授权均不代替日志批准，也不把开发时间冒充系统发布时间。纯内部协作Skill维护按仓库规则不生成公开功能候选。
- 协调者只组织日志与生成流程，不为写日志代开发、改业务代码或重跑日常测试。缺少必要证据时记录待补，不编造成功摘要。
