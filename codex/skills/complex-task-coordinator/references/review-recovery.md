# 审查异常恢复规范

适用受管代码审查中断、结果不完整、原生派发状态未知及补审失败。ACTIVE 只用原协调者身份与 `role_coordination_command`；人工查询只读，维护者修复机制不能代替协调者批准代码。原授权、串行门、完整覆盖及独立验证继续适用。

## 先分清发生了什么

从当前 action 的不可变终态、spec、state、逐批 diagnosis/session/log 取证，核对来源哈希和固定候选。分别列出：计划批次、已完成批次、失败批次、未启动批次，以及已观察到的真实问题。后续批次没有启动时，不称“漏收报告”，不推断零问题；服务正常退出也不等于审查成功。

| 事实 | 处理方式 | 停止条件 |
|---|---|---|
| 原服务仍在运行，或进程/派发状态未知 | 核 unit、PID/start 和原回执；保持原动作，等原生收口或由维护者核查 | 不并发重投、不清锁、不凭时间认定退出 |
| 普通模型请求超时，原服务已停止，初审允许两批并行 | 核同窗负载；按 `next_actions.recovery` 的真实诊断及新版串行方案，用 `service_resume` 补审一次，只复用完整证据 | 不能承诺降并发必然消除共享模型故障；补审再失败移交维护 |
| 原审查已经串行，或达到单批硬截止 | 先处理请求/模型服务或版本化入口的具体原因，再判断恢复；不能把同参数重跑写成修复 | 无实质处理不消耗唯一补审 |
| 上下文压缩、预算或工具失败 | 按原始 manifest 终因核实际输入、工具及有效上下文；由维护者处理入口问题 | 不减审查范围、不盲降推理强度、不无限加超时 |
| 配置、执行体、候选或证据身份变化 | 核实变化并按新身份准备；旧覆盖保留但不自动继承 | 不编辑冻结 spec 或伪造同一身份 |
| 已有明确代码缺陷 | 协调者核真实代码后在原开发授权内 `decide REWORK`，原执行者修复 | 新候选重新完成适用验证和完整审查 |
| 报告完整，待裁决 | 逐条核发现并走 `service_decide`，门禁满足后批准/合入 | 不重跑求零问题；不把覆盖完成当通过 |

负载快照只能证明该时段服务情况；没有请求级关联时，不把共享队列或网络猜测写成某一请求的确定根因。

入口升级须验证旧冻结格式读取与跨版本补审；不编辑旧 spec 迁就新入口，未知格式仍拒绝。

## ACTIVE 恢复步骤

1. 原观察器收集终态并保留故障事件和通知；协调者从 `next_actions` 读取 `evidence.path` 及原文，不反复 `service_collect` 代替诊断。
2. 核查原服务已停止、当前候选仍有效、原授权未过期/撤销且剩余额度足够；有在途或未知服务时保留原串行门。
3. 程序返回 `SERIAL_PARTIAL_RECOVERY_READY` 时，核其三类批次及 `repair`。它仅证明存在可执行的调度缓解方案，不能证明服务器已修复。使用建议 payload 调用 `service_resume`，新 action ID 关联原 action；运行时再次验证身份、证据、重复补审、授权与唯一服务入口。同一候选仍有未完成审查时，`service_submit` 不能用新编号或改背景另开全量审查，应先按原动作恢复；身份变化先交维护者核实。
4. 新目录冻结原代码、背景、规则及模型策略，记录串行补审和原 run。逐批复核可复用证据；只补失败、未启动范围。原失败保留，同一审查身份最多初审加一次补审，不建立第二套轮询器。
5. 取得原生提交回执后才说“补审已启动”；检查实际子进程及批次进展。完整报告返回后由协调者逐项裁决；通过后才继续合入和依赖任务。补审失败或证据不明则保留门禁，停止原样重投，向维护者说明具体缺口。

串行补审只改变调度，不提高超时、不更换模型、不减少覆盖，也不新增调用额度。它减少同一审查内部竞争，无法消除其他应用负载。修复业务问题和维护审查基础设施分别留证，互不冒充。

## 责任、通知与接续

- **程序负责**：按真实进程收集终态、核来源、生成三类批次与恢复提示、约束一次补审、保留事件和同源通知。只读提示不启动审查、不消费额度、不生成通过结论。
- **协调者负责**：读证据、选择已验证恢复或返修、执行原生动作、确认真实进展，并在自然安全点保存未完成动作与依据。已接收明确用户答复不得要求重发。
- **维护者负责**：原生服务、模型请求、工具/配置或证据链异常；原协调者本身请求无响应时先核实际执行及写操作，按原生停止/恢复边界处理，保留工作单与未知副作用，不复制身份代执行。
- **通知**：首次故障通过现有故障 outbox；新增原因、恢复提交、再次失败或责任移交按现有有意义事件汇报。送达仍按现有额度、回执及夜间规则，不额外重复群发。内部故障不要求用户“接受部分覆盖”。只有真实范围、合同、费用/额度或外部权限变化才提出具体问题。
- **继续工作**：无硬依赖、无共享写冲突的任务继续；相关依赖保持等待。没有可执行恢复时写明维护责任人、下一动作和复核触发条件，不能无限静默等待或反复承诺下轮必生效。

对外用普通中文，例如：“三批已完成，两批请求超时，另两批尚未开始。协调者将保留已完成结果，一次一批补齐剩余审查；报告完整后再决定是否需要返修。”编号、哈希与原始诊断码保留在证据附件。
