# 架构设计与三槽任务拆分

用于调查、设计或修订并发计划。运行时派单按项目 inbox/PROTOCOL.md，由协调者 Skill 执行。

## 1. 固定本期边界

先按 [需求边界与目录规则](requirement-boundaries.md) 决定独立建包或更新原包；代码仓路径、需求文档根、实际运行project_root分开核实。跨需求依赖不改变本包归属，也不自动扩充本期AC。

先恢复用户意图和项目现状，不从全量模块清单开始设计。记录：

- 业务输入、触发方式、最小处理路径、最终可使用的输出，以及谁怎样验证输出。
- 本期必须达到的 REQ/AC，明确不做及后续 DEFERRED 项。
- 已授权动作、集成位置和结束条件；未知现场证据阻塞哪些任务。
- 复用的现有组件、已验证能力、拟新增能力。引用真实文件/符号，不能把历史文档当作当前运行证据。

优先一个真实样本或代表性请求走完整链路。最小链路包含适用的失败和恢复行为，不等于只演示成功分支。

## 2. 只提前做会影响本期正确性的设计

接口/状态语义、数据身份与唯一性、幂等、父子关系、错误恢复、迁移兼容和共享资源所有权应在相关任务前明确。高风险假设先安排最小验证；验证条件不足则列探索任务或阻塞受影响工作。

涉及数据库增长时，根据实际新增数据讨论主键容量、必要唯一约束/查询索引、有限分页，以及高频明细与核心实体是否需分开。已有大表的兼容问题必须有首期处理或明确证据，不仅写“以后优化”。分库分表、分区、冷热系统仍需规模证据，不能自动纳入所有项目。

扩展点围绕已知后续变化保留最小稳定契约，不为未知变化实现完整插件平台。复用项目现有任务、租约、日志和发布机制，不新建通用协调服务。

## 3. 按可验收产物拆分

每张任务卡必须有：稳定 ID、REQ/AC、阶段、依赖、输入和基线、最小阅读集、修改范围、关键契约、产物、验证、停止/升级条件和文档回报要求。

- 任务服务一个可验证行为，可以包含必要的成功/失败路径。不要机械拆成“所有表 → 所有接口 → 所有测试”。
- 契约提供方在消费者之前。尚未完成的接口只能用明确约定的替身做局部验证，不能宣称联调通过。
- 聚合父任务只负责汇总和综合验收；它不再次分派完整实现。
- 必须共享文件的任务先后执行，或拆出明确的契约/接线 owner。不能仅因工作树不同就声称可以并行。
- 一个任务缺关键信息时不设 READY；独立且输入已齐的任务继续安排。

任务可以拆 A/B 子任务来减少真实阻塞，但不增加产品范围；拆完需同步父任务、依赖、验收和接续表。运行时协调者在原REQ/AC、已接受契约和已授权阶段内主动细化剩余任务，按实际空闲角色补位，具体规则见协调者Skill的 [运行时任务拆分](../../complex-task-coordinator/references/task-decomposition.md)。初始三槽计划不限制后续正常调整；在途工作先确认检查点交接，关键契约或架构变化仍升级。

## 4. 用三个独立槽而非固定三支队伍

为 A/B/C 推荐首波，但 owner 不永久绑定模块。只保留一个正在写业务代码的任务给每个执行者。

派单候选必须同时满足：

1. 在当前已授权阶段；
2. 所有硬依赖已验收，产物在指定基线可用且证据未失效；
3. 输入和允许动作齐全；
4. 没有重复 owner、共享文件/迁移链或资源冲突；
5. 执行者已经明确可接任务，不仍在审查、返修或运行进程。

候选排序先推进最小链路的关键路径，再考虑能否解除其他任务阻塞和执行者已有上下文。没有依据时不硬编码一套跨项目优先级。

至少交付以下三个视图，全部从同一 TODO 依赖表维护；另为测试槽标明何时取得稳定快照、需要哪些环境和证据：

| 视图 | 必须回答 |
|---|---|
| 完整依赖图/表 | 每个任务依赖谁，哪些是聚合、探索或后续阶段？ |
| 三槽首波与接续 | A/B/C 起点是什么，谁先结束后可能接哪些任务？ |
| 完成事件 → 候选 | 某产物接受、阻塞解除或契约改变后，需要重新计算哪些任务？ |

候选不是自动解锁；必须重新检查全部条件。避免要求整波所有任务结束才派下一项，除非确有共同门禁。

开发并发、测试并发与资源并发分开：三名开发执行者不意味着三个迁移、模型/GPU任务或共享环境部署可以同时运行。测试者只占独立测试槽，不作为第四名开发者；其测试派单必须绑定固定提交或集成候选，不能对移动分支取证。资源限制及申请/释放方式按项目事实写入 DESIGN 和任务卡。OCR 固定由协调者串行管理，执行者等待审查和返修；OCR 串行不要求业务开发或独立测试也串行。

强模型默认审查已完成开发与常规测试的功能批次，以及必要的端到端组合行为；明确具体风险才标对应合入或阶段门禁，用户明确要求时才设计实现前契约审查。冻结既定需求/AC，按共同调用链合批；纠错只补原功能与必要验证，范围外建议不派单、不抬高完成标准。门禁不默认占用三个开发槽，不把每张任务卡变成付费审查；判断和收口按协调者Skill的纠错审查约定。

## 5. 工作区与契约交付

具备 Git 时，开发执行者必须自行从任务指定基线新建专属开发分支，优先建立独立 worktree。测试者使用独立只读测试工作区或固定集成候选，不在测试过程中修改业务实现。协调者作门禁决定后负责合入已核实的主分支；开发执行者和测试者不能自行合入。共享通信目录使用唯一绝对路径，不能让 worktree 各自拥有独立状态副本。没有 Git 时，明确分支能力缺失及所用产物版本机制，不能假称满足 Git 分支验收。

设计中写明主分支、分支创建责任、验收门禁与OCR配置/拆批方式、强审查入口及开发日志位置；默认人工强审，用户自定义时间或任务授权内由协调者通过统一限额脚本调用Codex，滚动60分钟最多5次，汇报授权与次数。未配置能力标为前提，不编造调用；审查授权不代替开发/删除/部署/正式日志批准。运行角色按项目协议执行门禁。

迁移链、路由总入口、公共枚举/配置等存在多人碰撞时，为它们指定单一 owner和转交条件；根据项目实际决定，不硬套固定文件列表。接受后再更新消费者基线。

契约修改由执行者提交建议，协调者修改 DESIGN、记录版本和受影响任务。已经通过的验收若失效，应撤回相应 DONE、暂停消费者并重新验证，不能只更改文字继续开发。

## 6. 设计交付检查

- 需求ID、绝对根、权威TODO、关联包与运行绑定明确；独立目标不混入旧包，共用角色与代码仓不成为合包理由。
- 每个本期 REQ 有 AC 和任务，所有依赖存在且无环；验收可由实际证据判断。
- 首波不超过三个可执行叶任务；不足三项时说明真实串行门禁，不人为制造任务。
- 文件/资源 owner 无冲突，接口提供与消费顺序成立，结束节点完整。
- 后续阶段保持 DEFERRED，本期不把额外界面、工具、重构或架构平台变成前置。
- 所有五会话都能仅凭启动入口找到共享根、角色、派单、回报及下一步。
- 原有文档里的旧授权、旧 DONE 和历史测试次数不能与新状态混用；纠正矛盾，保留必要来源。
