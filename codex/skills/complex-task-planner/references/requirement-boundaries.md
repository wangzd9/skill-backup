# 需求边界、文档归属与运行交接

接到新需求或修订范围时，在创建/更新 PRD、TODO 之前读取。需求目录按可独立交付和验收的业务目标划分；代码仓、产品、版本和运行群分别记录，不能拿其中之一替代需求归属。

## 1. 先判断归属

| 情况 | 文档动作 |
|---|---|
| 新增可单独验收、暂停或发布的目标；有独立范围/完成条件 | 建独立需求包。引用关联包和已接受契约，不把整套内容追加到旧包 |
| 为满足原REQ/AC所需的缺陷修复、漏项或必要证据 | 更新原包任务/返修记录，保留原ID和attempt，不为每个bug另建需求包 |
| 原业务目标的后续阶段、批次或版本 | 仍在原包内按阶段/任务/运行批次组织；若实际形成独立目标再拆包。版本号本身不是拆包依据 |
| 同仓跨模块/跨需求依赖 | 各包保留唯一归属，用需求ID、契约版本及固定产物证据关联，注明接口/共享文件owner和集成责任 |

同一个仓库、同一批执行者、同一模型服务或代码依赖，均不足以证明应合成一个需求包。独立需求也不等于每条REQ都建全套目录。用户明确指定的现有包/路径优先；若指定路径是代码仓或文档容器，应按项目既有约定选择包目录，不把容器误当需求根。关键归属仍无法确定才澄清；其他情况直接说明判断并执行。

## 2. 默认路径与最小入口

无用户指定结构时，独立需求默认放在 `doc/prd/<独立需求名>/`，与已有需求同级。代码仓内已有 `docs/<feature>/` 等约定时沿用。只有明确的父子业务目标才嵌套；不把“最早创建的需求”当作整个产品的父目录。

例如代码都在 rosbag-catalog，独立 A100 部署需求仍可放在 `doc/prd/rosbag-catalog-a100-multi-node/`，不因最近在 `rosbag-catalog-integration/` 工作而塞入其主文档。现有 `rosbag-catalog-integration/a100-multi-node/` 已有独立包，可保留原路径接续；这是存量兼容，不是新需求默认路径。水雾的一次1012测试是运行批次，不因此再建一套平台PRD。

用 [需求入口模板](../assets/requirement-readme.md) 写清：稳定需求ID、目标/本期范围、代码仓、本需求绝对根、权威TODO、已接受契约入口、关联需求与跨包依赖、运行绑定情况、阶段接续条件。相对目录好看不能替代实际绝对运行入口。

新包需要五角色协作时采用现有工具支持的布局：

```text
doc/prd/
├── README.md                       # 需求导航/选择入口，不放业务任务状态
├── <独立需求甲>/
│   ├── README.md                    # 本需求身份、边界与入口
│   ├── PRD.md / DESIGN.md / ACCEPTANCE.md
│   ├── TODO.md / HANDOFF.md / SESSION-START.md
│   ├── ROLE-BINDINGS.json           # 实际值；未绑定明确说明
│   ├── inbox/                      # 协议、角色派单、ACK与控制材料
│   ├── receipts/ / test-receipts/ / reviews/
│   └── sessions/ / events/          # 按实际绑定使用
└── <独立需求乙>/                    # 同一规则，自有任务与交互证据
```

目录按需创建；规划阶段不制造空回执/会话，不复制旧租约、运行状态、授权或群/cron ID。绑定模板的角色/Skill版本按现场核对，不将模板示例视为已部署事实。包内交互用同一 TASK-ID/attempt 关联，README给出定位。当前脚本没有自动扫描任意 `tasks/<id>/` 或父协作目录的能力，不能仅改目录就声称兼容。

## 3. 单一来源与跨包依赖

- 每个需求包自有REQ/AC、TODO和证据。项目/产品索引只列需求ID、目标和链接；实时状态若需展示，使用明确来源的只读投影，不人工抄第二份任务状态。
- 公共契约保留已确定的唯一来源，其他需求按版本引用；有已维护的产品公共契约区时使用它，不为整理目录另造通用平台。改变公共契约时写明影响包、兼容/迁移和复验责任。
- 跨包依赖写“需求ID/任务ID、所需产物、固定commit/契约版本、接受证据位置和失效条件”；不能只写“等另一个需求完成”。各协调owner维护自己的包，不能直接把关联包任务标DONE。
- 当前HANDOFF、启动入口只保存有效规则和最近检查点，旧过程进入时间线/历史归档；已确认失效的规范从当前入口替换，不长期堆叠多轮覆盖声明。
- 新包初建由规划者写入；已有活跃包先核对协调者单写和现有租约，修订交当前协调者受控写入，或在安全检查点明确交接写权。拿不到租约不抢占、不另造可写状态副本；可在独立规划记录保存建议，交接接受前不宣称现行契约已变。用户本次补充原目标的AC时记录补充来源，不追溯冒称旧AC已包含。

## 4. 文档建包与角色激活分开

建独立需求目录不会自动建立新的五个群或五套cron。通常复用既有角色资源；规划交付写清当前绑定/未绑定、等待里程碑和允许接续动作，后续阶段保持DEFERRED。新绑定模板默认control=PAUSED，只有实际配置、授权与启动检查就绪后才按既有流程启用；不改动已有包的真实控制状态。规划完成不自动派单、迁移运行入口或授权生产。固定池允许用户明确选择已登记的README方案包，缺TODO/协议/验收材料标preparation_required，由协调者先准备规划契约再派单；这不把仅有入口的包说成已可开发，也不由脚本编造任务。

业务工具仍校验实际 `<project_root>/ROLE-BINDINGS.json`，读取该根TODO、角色inbox及回执。固定角色池的catalog_path可指向`doc/prd/README.md`导航，但索引不成为业务project_root；池运行时把已登记需求解析为具体runtime_root及各角色业务根。未激活包写明拟用根和未绑定，角色/job字段不编造。

存量包显式共用兼容runtime_root时，在本包TODO用“本包任务编号定位：`TASK-xx`、`TASK-yy`。”登记完整精确ID，作为当前可执行范围；新任务先更新该定位，不能用前缀涵盖未列出的子任务，也不复制旧业务状态。列表缺失时不允许恢复同根旧任务。`context-input`据此隔离其他包的任务、派单、continuation与旧checkpoint；共享历史仍可作为引用证据。独立新需求根沿自身TODO工作。

固定池统一持有五角色稳定群/job；用户在协调者群当前全权消息明确选择需求后，由专用可信入口持久排队，在旧任务安全检查点自动切换，无需每次手工重绑五角色。业务材料始终留在所属需求包；请求受理不等于切换已完成。选择接受后后台cron沿该需求持久scope接续至完成、暂停或撤销，后续cron不要求逐轮群全权；普通群问题仍只读。详见[固定角色池](../../complex-task-coordinator/references/role-pool.md)。

存量首次纳入池的维护过程仍核对注册表、原生job、群/session和角色实际根，保留原ID、暂停状态与在途身份；此核实不成为每次规划或切需求的新人工步骤。不向多个包复制相同chat/job制造多重可写绑定；固定池一次选择不等于任意多包并行。跨包订阅仅按显式规则读取，不授予跨包写权。

## 5. 存量整理与交付检查

存量混合包先做归属/路径索引；是否迁移按用户任务范围决定，不把整理Skill扩成生产路径迁移。真迁移时列旧→新映射，在安全检查点迁移完整包并同步引用、绑定、注册/cron、巡检与恢复入口；原ID、快照、审查、授权范围和历史证据保留，先验证再切换，不复制两份可写状态。只有导航不算迁移完成。

交付前从无聊天历史的接续者视角核对：能否确认本需求与代码仓的区别、唯一任务状态和允许写入范围；跨包依赖有无实际产物/接受条件；运行根是否与工具读取路径一致；未绑定、后续阶段和迁移是否如实标记。文档链接/映射检查足够时不启动业务测试、真实群消息或模型审查。
