# 数据库体积专项核查

核查时间：2026-11-02 13:35 起，UTC+08:00。对象为角色流程账本 `business.sqlite3`，全程只读，没有删除、迁移、整理在线数据库或更改运行配置。统计查询分别读取，运行系统持续变化，行数与大小不作为严格同一事务快照。

## 结论

**3.18 GB 对 SQLite 本身并不构成异常，但对当前这个流程账本明显偏大。主要原因是旧版工作输入重复保存大正文，不是有这么多独立业务成果，也不是文件里有大量删除后留下的空洞。**

这些历史记录具有追溯和防止命令重复执行的用途，不应整体删除。但其正文保存方式存在已实证的重复，值得进行保留证据的历史瘦身。新增工作输入已使用引用方式；历史大正文尚未迁移。

## “里面的数据都有效吗”应分三层回答

1. **结构是否健康：** 本次快速检查通过。没有做全量业务语义核验或完整附件引用核验，不能据此保证所有记录内容正确。
2. **是否还有保存用途：** 命令表保存稳定命令身份、输入指纹、原始结果和决策回执。当前代码会读取旧结果判断重放或冲突，回执也使用命令行号。因此旧记录仍可能被恢复或审计读取，不能按日期直接删除整行或清空表。
3. **保存方式是否冗余：** 是。只读抽查三条历史大输入，大小均约 5.54 MB，几乎全部是事件正文；三页共包含48次事件内容，按完整事件内容哈希比较只有17份不同内容。事件正文合计约16.60 MB，去重后的独立内容约5.53 MB。这证明样本有重复，**不是证明全库均可按同一比例缩减**。

样本页各自的完整哈希不同。只对整页做内容寻址，仍会保留大量跨页重叠事件；真正降低总占用，需要考虑原始事件内容的共享保存或无损压缩，并保持原页可精确还原。

## 建议操作顺序

**第一步：先在一致备份副本上做迁移预演。** 使用 SQLite 一致备份机制，并收集它实际引用的不可变附件及哈希。在线文件不能简单复制后就当作已验证备份；有数据库备份也不等于附件已备齐。

**第二步：保留历史命令身份，只优化大正文存储。** 优先处理旧工作输入中的事件正文，保留命令编号、输入指纹、创建时间、行号、原有决定和结果字段。沿用已有不可变引用与读回机制；若增加压缩或逐事件共享格式，先实现并验证兼容读取，不能直接把现有 JSON 附件改成压缩文件。

**第三步：证明迁移无损且没有转移容量。** 对迁移前后展开结果逐条校验；验证重复命令不会重新执行，冲突输入仍拒绝，分页、确认水位、回执引用和恢复均不变化。分别统计数据库、附件、压缩归档和保留备份的总体积。只把 3 GB 从数据库移到附件，不算总磁盘瘦身；保留一份原始备份时，预演阶段总占用可能暂时增加。

**第四步：在安全维护窗口切换经过验证的精简副本。** 先确认没有未核清的写入和在途资源，冻结后核对版本及事件水位，处理预演之后产生的增量，才能切换。切换必须覆盖原数据库的全部新记录，不能用一份较早备份覆盖现在线上进度。保留完整回退方案。

**第五步：把归档与容量规则固化到机制。** 新数据继续限制大正文写入，完善附件公平扫描和完整度显示，增加增长监测及可还原归档。历史命令和其引用附件的清理要以保留策略、引用关系和恢复验证为依据，不按文件年龄直接删除。

## 现在不建议直接做什么

- **不清空命令表，不批量删除旧记录。** 这会破坏命令重放判断、审计和部分回执定位。
- **不把 `VACUUM` 当本次主要修复。** 当前几乎没有空闲页；页内也有少量余量，但不能靠整理消除近 3 GB 的实际正文。应先完成保留证据的迁移，再在副本或维护窗口回收空间。
- **不删除看起来过期的输入附件。** 当前明确将它们视为审计存储，旧命令可能继续引用。
- **不承诺最终缩到某个 MB 数。** 需在副本上完成全量去重/压缩及兼容验证，才能给出数据库和总占用的实测收益。
