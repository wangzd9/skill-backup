# Token 消耗与前轮优化效果复核

采集截止：**2026-11-02 13:55:24，UTC+08:00**。本次只读分析用量、限定上下文样本和历史上线证据，未修改模型、运行配置或业务流程，未调用模型制造比较样本。

## 结论

**前一轮优化有明确的局部效果，但还不能证明系统已稳定做到“同等质量、更快交付、总 token 更少”。**

- 已证实：10月30日上线的去重机制，能让同一冻结输入的字节体积下降约9%～11%，完整展开后与原输入相等；当前样本也仍在采用该机制。
- 已观察到：协调者本地业务请求输入中位数，从10月29日的96,486降到10月31日至今的81,525，约下降15.5%。这是同角色、同路线的观察值，任务及阶段不同，不能全部归因于优化。
- 尚未证实：每个完整交付的全链 token、交付耗时和质量在可比任务下同步改善。优化前后完整日的总量并没有稳定下降，开发、测试和等待阶段也不能直接相互比较。
- 下一步最有价值的是**减少无条件变化时的模型启动、把整份需求上下文改为当前动作所需材料、减少机械纠错并采用接续记忆**。压短正常答复、减少总结或削弱测试审查，不是当前主要节省方向。

## 一、统计口径

主来源为 `/home/wang/.hermes/runtime/role-usage.db`，按请求开始时间归窗，以物理请求身份统计，不叠加会话累计值。用当前规范化函数核对字段存在性，未上报用量不按零计算。

本报告的“输入”是已知 `prompt_tokens`，包含可能被缓存复用的上下文，**不是未缓存计费输入，也不是费用**。缓存读取属于输入的一部分，不能再加一次；未单独报告的推理字段也不能据此算作零。

主要当前窗口是10月31日00:00至11月2日13:55，约61.92小时，不是完整72小时。历史比较另外使用完整日期。用量库在单个只读事务内读取；上下文与独立审查文件随后采样，不共享跨库原子快照。

角色用量与独立代码审查分开记录。独立审查按响应时间归窗，采集仅覆盖现有诊断能够定位的会话；不冒称全系统所有模型消耗都已完整覆盖。

## 三、前几天那轮优化到底有没有效果

这里以有明确上线记录的**10月30日0.14.0输入优化**及后续接续、异常恢复改进为主要对象。原始上线记录见[优化实施说明](../coordinator-health-audit-20261030/TOKEN-OPTIMIZATION-IMPLEMENTATION.md)。后续多个版本同时发生变化，不能按发布时间把全部收益只归给一个版本。

### 1. 同一输入的无损减负：有效，有直接证据

原发布对同一冻结快照做过比较，包含新增投影元数据：

| 角色 | 原始体积 | 优化后体积 | 字节下降 | 还原核对 |
|---|---:|---:|---:|---|
| 协调者 | 199,464 bytes | 181,313 bytes | 9.10% | 完整展开相等 |
| 测试者 | 95,404 bytes | 85,649 bytes | 10.22% | 完整展开相等 |
| A/B/C当时样本 | 各72,682 bytes | 各64,945 bytes | 10.65% | 完整展开相等 |

这是可靠的机械减负证据。**字节下降不等于同样百分比的实际 token、计算量或费用下降**；启动包之外还有角色指令、系统提示、工具定义、历史消息和后续证据读取。材料可恢复也不能单独证明模型的实际判断质量完全等价。

当前抽查五个角色各八个最近业务会话，40份均有可解析启动包并带现有投影信息。投影元数据所记的减幅中位数分别约为：协调者6.65%、A 10.28%、B 1.66%、C 12.82%、测试者10.40%。这些是**未计新增投影元数据的紧凑JSON字节减幅**，与上表净减幅口径不同；只证明仍在采用和收益随内容变化，不能横向直接比较或换算成token。

### 2. 协调者单次负担：有下降信号，不能当因果节省率

比较10月29日完整一天与10月31日至采集时点，均只取**本地路线、后台业务回合**：

| 角色 | 优化前每请求输入中位数 | 优化后每请求输入中位数 | 观察变化 |
|---|---:|---:|---:|
| 协调者 | 96,486 | 81,525 | −15.5% |
| A | 131,247.5 | 109,846 | 下降 |
| B | 99,782.5 | 109,759 | 上升 |
| C | 128,827 | 59,733 | 下降 |
| 测试者 | 71,149.5 | 103,351 | 上升 |

协调者第一条业务请求的输入中位数也从76,583降到65,641，约下降14.3%。11月1日协调者本地业务请求中位数为65,330，最近24小时为70,763；长尾及日间波动仍在。

这些比较已经避免混入云端和群聊，但仍不是同一任务的对照：需求大小、候选历史、开发/审查/等待阶段、工具调用数量和运行版本都变了。C下降很多不等于开发能力或交付效率提高同样比例；测试者上升也不等于优化失败。

### 3. 全日总量：部分日期下降，尚无稳定净节省证据

| 完整日期 | 角色会话物理请求 | 已知输入 |
|---|---:|---:|
| 10月27日 | 1858 | 1.783亿 |
| 10月28日 | 2401 | 1.973亿 |
| 10月29日 | 3255 | 3.412亿 |
| 10月30日，包含上线前后 | 2897 | 3.531亿 |
| 10月31日 | 2508 | 2.760亿 |
| 11月1日 | 3083 | 2.485亿 |

如果只比较10月29日和11月1日，会看到下降约27.2%；但优化前10月27日至29日日均约**2.390亿**，优化后10月31日及11月1日日均约**2.622亿**，反而高约9.7%。两者都受工作量和角色阶段影响，**既不能挑高峰日宣称整体省了27%，也不能据日均上升认定优化导致更费**。

因此，目前可以确认“优化被采用、部分机械负担和协调者单次输入下降”；不能确认原先10%～20%的全链token目标已经达成，也不能声称在相同交付质量下整体更快更省。

更早10月19日报告中的约28%～33%收益依赖“每类动作可少一次模型往返”等假设，是理论估算，不能当成已实现比例；当时的服务端缓存样本也不能代表当前全部请求。

## 四、为什么优化后仍然耗得多

**第一，去重只减少了一部分包内重复，整份需求上下文仍会多次进入请求。** 当前最近一份协调者启动消息约163.5 KB，其中业务包约111.1 KB；业务包中的任务约29.4 KB、计划约24.3 KB，两项合计约占包体48%。这些字节不能直接换算成token，但表明只去重长正文，还没有把输入组织成“当前动作的必要材料”。

**第二，接续请求仍会重带已有上下文。** 优化后协调者本地业务请求里，首请求已知输入约5346万，后续请求约2.35亿，后续部分占约81.5%。后续请求包含必要判断、阅读和真实动作，不能全称浪费；它提示应同时优化工具往返和上下文增长，而不只优化首包。

**第三，等待和进展还没有完全分离。** 整体审计已确认，当前等待主要依赖自由文本、较宽的事件相关性及确认水位。反复读到事件、保存检查点和真正解除业务依赖不是一回事。此前账本样本里的663次协调者执行，不能全算空转，但值得按等待对象进一步分类。

**第四，结构化接续记忆没有被采用。** 本次40份限定会话样本均未带结构化工作记忆核验信息；此前36份新工作单也全部未采用。自由文本容易复制旧判断，并在下轮重新定位材料。没有记忆信息不等于会话完全没有检查点，但已有接续能力没有发挥预期作用。

**第五，错误纠正仍会增加请求。** 此前截至11:56的三天账本样本记录39次未发行水位拒绝、分页与控制字段错误，日志也有临时SQL误猜字段。它们说明机械参数准备仍可改进；不能仅将错误次数乘平均token后当作已证实浪费，因为不同请求的上下文、缓存和后续动作不同。

## 五、不降低效果的优先优化顺序

| 顺序 | 改什么 | 保留什么 / 如何验收 |
|---|---|---|
| 1 | **等待先由程序判断，条件变化再唤醒模型**：等待对象、所需状态、负责方、解除断言和复核时间结构化 | 相关结果下一正常调度周期可见；到期仍复核；暂停、撤权、未知动作及未读确认不变。减少无关唤醒，不统一拉长等待 |
| 2 | **按当前动作准备材料**：启动先提供当前任务、待办和必要事实；历史及无关长描述用可核验引用，沿已有决策上下文接口展开 | 当前失败/未知、权限边界、任务负责方和依赖仍明确；需阅读的证据可精确获取，不能凭引用冒充已读。执行前仍核权威事实 |
| 3 | **减少机械往返和纠错**：程序准备精确候选、水位、分页回执及参数草稿；独立只读查询同轮合并 | 语义决定仍由角色作出；有先后依赖的动作保持顺序；错误对象及未读页继续拒绝，不靠降低检查消除报错 |
| 4 | **启用已有接续记忆**：保存已做动作、证据定位、版本/环境依赖、未解决条件和下一处工作 | 版本、证据、环境或授权变化时失效重核；不跨角色复用独立测试结论。避免仅降低会话上限、导致更多重启重读 |
| 5 | **保持稳定前缀并清理业务指令重复**：固定角色指令/工具结构稳定排列，动态状态放后；同义重复以单一合同为准 | 先核验真实发往模型的输入，不只看脱敏钩子片段；关键约束和必要知识保留。测首响应及缓存，避免输入变短却缓存更差 |
| 6 | **统一环境与异常接手**：一次准备、复用真实诊断、恢复后再验证 | 保留真实失败和独立性；未知执行先核清。减少因环境误判、错误重试和重复询问引发的回合，沿整体审计方案实施 |

按当前协调者本地业务请求中位数，**少一次已确认不必要的请求，逻辑输入的量级约8.15万token**。这只是说明优化杠杆，不是每次可固定省这么多，也不是GPU或费用同比下降的承诺。

这些建议应先从可完整还原的机械改动做起，再逐步验证输入组织调整；不能仅凭“没有换模型、没有减测试”就宣称质量和效率绝对不受影响。

## 六、缓存和数据库体积需要单独看

当前窗口记录的缓存读取有明确字段覆盖的只有189次，**都在云端路线**；6449次本地角色请求没有严格缓存字段覆盖。本地缓存未知不等于没有缓存，云端已知样本约95.4%的缓存读取比例也不能套到本地。

因此，6.20亿是角色会话已记录的逻辑输入，不应全部乘云端价格，也不能据此宣称GPU实际处理了6.20亿新token。优化还应观察请求级排队、首响应、生成和缓存数据；只减已缓存的稳定前缀，实际计算节省可能有限。

数据库3.18 GB的大头是历史工作输入重复留存，[容量专项核查](DATABASE-STORAGE-ASSESSMENT.md)已经确认。历史正文去重/归档主要解决磁盘与恢复维护成本；不能把数据库缩小比例当模型token节省率。模型token要从实际请求输入另行测量。

## 七、下一轮如何证明“更省且不影响效率和效果”

需要同时建立三层比较：

1. **同一冻结输入比较：** 原样和优化样可完整还原，使用同一个真实分词器测输入及工具定义，保留所有必要事实。不要用字节比例代替token。
2. **同类完整工作比较：** 按角色、模型、任务类别及阶段分组，统计全部输入/输出、补读、工具回合、重启、重试与返修；同时报告缺失字段和独立审查用量。不能只看更轻的首请求或截取工作的一部分。
3. **交付质量与耗时比较：** 验收条件、真实测试、审查覆盖及独立性保持；比较首次验收、最终发现的问题、用户重复介入、到达可执行状态的延迟和最终交付时间。出现漏证据、返工增加或延迟变长，应调整或撤回相应优化。

完成这些比较前，建议将当前结果表述为：**已实现局部输入去重，观察到协调者单次输入下降；无损的全链净节省尚待验证。** 本轮新增的是分析与整改依据，没有部署上述新优化。
