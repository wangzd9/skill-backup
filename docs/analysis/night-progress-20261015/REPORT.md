## 已证实的瓶颈

### 1. 审查完成信号没有接入观察器，自动接续失效

观察器 `collect()` 对 `reviews` 只遍历 `*.md`。OCR后台完成主要更新 `state.json`、`b01.log` 等，现有运行索引指向run，但观察器没有把该run终态纳入通知指纹。

证据链：补审state记录01:59收口 → 之后无协调者API请求 → 原生cron仍持续运行 → 保留的05:15—07:55共33轮明确输出“agent skipped” → 08:00—08:30继续skip → 08:34人工消息 → 首次裁决08:36。部分更早cron正文已被输出留存策略清理，不能声称逐份查看了02点的正文；执行表与API记录仍保留该期间无接续的交叉证据。

这是“变化检测的覆盖不完整”，不是简单把五分钟改成一分钟能解决。夜间只静默通知本身符合约定，静默不应成为漏消费结果的理由。

### 2. 覆盖完成被误当成没有问题，验收质量没有形成闭环

补审日志实际有11条finding，包含两个HIGH；首发裁决只看diagnosis的coverage信息，误写为零finding。08:52更正已明确记录：真实storage相对路径与物理根拼接错误、移动恢复检测失效、用途回显遗漏、409判定顺序等需要纠正。

TESTER使用真实MySQL并通过166项用例与8个探针，是有效的局部证据；但未证明真实路径口径的关键不变量。旧夹具存绝对路径而生产存storage相对路径，导致测试通过却没有覆盖真实恢复行为。**不能用测试数量、真实数据库或OCR进程成功退出替代业务行为验证。**

更正版裁决对“6条”与编号集合中LOW顺手项的写法仍有细节不一致，本报告不重新裁定问题数量；确定事实是：首发零finding不成立，存在已确认阻塞，接受已撤销并返修。

2026-10-15修复验证补充：新只读提取器逐条核对三批原日志与session，实际11条的原始分级为 **2 HIGH / 5 MEDIUM / 4 LOW**；历史裁决摘要中的“2/4/5”也有计数错误。原裁决及采证快照保持原样，不改历史证据；完整提取结果见[修复验证材料](../night-continuation-fix-20261015/evidence/overnight-results.json)。这不改变协调者对具体问题是否阻塞的裁决职责。

### 3. 并发容量被依赖链限制，没有自动变成三路开发

F原任务卡明确依赖E接受并共享文件；B无授权自行抢写。C的真实材料缺口也不能靠编代码补造。空闲三个执行者不意味着当前授权范围必然有三个可并行实现。

协调者应在稳定交付形成后检查能否拆出不冲突的F测试/接口准备，或派既有D1可测试性复核。D1记录一直写“TESTER复核待派”，而测试者21:00—23:44未占用；这是可评估的接续机会。该复核不能消除真实材料缺失，也不能据此提前宣布D2完成。

### 4. 租约故障和核账消耗了协调者时间

一次授权核对耗时约29分钟，其中存在租约过期、长sleep、恢复和重复读文档。协调者还独立复跑A已跑、TESTER随后再跑的12+154用例。应保留快照与证据核验，把常规行为复跑交独立测试者；不能把所有后台活动都算成推进。

## 不能从现有证据断言的事

- 无法得到每个请求的纯vLLM排队时间；本地API总耗时不能替代服务端accepted/dequeued/inference边界。
- 初审硬截止约65分钟已证实；“同期1012大包持续INFER争槽”仅是协调者总结中的解释。C在21:08已有 `active_runs=[]`、编排退出及DB状态滞留证据，残留 `INFER RUNNING` 不能证明夜间真实推理。缺少该失败窗口服务端请求级指标，不能将此解释作为最终根因。
- 协调者有一条从14日16:28开始、缺结束记录的API行。它不应算作整夜持续请求；本报告排除未闭合记录。若简单把open请求延续到08:00，会错误多算660分钟。
- 自动早报把协调者660分钟全部映射为waiting，把测试者工作状态 `ACKED_RUNNING` 留在unknown，A也有约487分钟unknown。原因包含旧派单未归档、mtime错配和状态分类不完整，不能拿这份机械统计直接判断所有人整夜空闲或持续工作。本报告通过原生会话、真实任务产出和依赖交叉重建，没有倒填原记录。
