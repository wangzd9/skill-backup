证据源哈希按流读取，仅普通文件，单次预算 64 MiB；缺少不可变哈希、超预算或读取失败标为 UNVERIFIED。核对文件描述符及路径前后身份、大小和时间，检测读取期间变化。完整工件始终可展开，读取不 ACK、不执行服务。

## 补验异常如何退出

新增 `workflow_verification_exceptions.py`，复用既有退休、调度、开发策略、独立验证、合入和通知入口。

1. 原生补验把 UNVERIFIED 结果保存后，登记 `VERIFICATION_EXCEPTION_RECORDED`，绑定原 request、work、候选/head、runner 和证据哈希，明确后续责任为 COORDINATOR。旧原生结果可由 sweep 恢复登记，不再次执行测试。
2. 同一事务请求旧验证安全退休。存活 TESTER 通过原 `safe_release` 退出；运行时只在实际 execution/tool writer 围栏清除后退休工作、释放角色。worker 退出本身不产生业务完成或返修。
3. 协调者读证据后调用 `resolve_verification_exception`：`repair`、`investigate` 或 `close`，必须有语义原因。
4. `repair` 针对本 run 当前已合入、已 COMPLETED 的供应任务。只允许原范围内明确路径，要求仍有效的本地开发策略和有审计依据的集成基线。先登记处置，再等待原补验工作及返修供应任务的旧工作与执行核退，事务内产生真实新 attempt/PENDING 派单；原 owner、scope、AC、required_checks 不变。无需等 MN-07 先失败。
5. 延后落实的前提失败，登记 `VERIFICATION_EXCEPTION_REPAIR_BLOCKED` 和恢复责任；不把“文字里提到 a8”当成已派单。调查必须填写下一行动，300 秒后允许一次复核唤醒，之后无变化仍遵循退避，不无限空转。
6. 新候选仍走独立测试、审查/批准、合入及交付原门禁。旧补验已核退后，沿原请求谱系排队复验，不伪造一个 FAIL 作为前置。
7. `close` 必须引用同原补验请求、发生在异常之后、当前供应候选的真实 `supplemental_mysql` PASS，重新核原 runner 证据。同一请求后续再返修的当前真实 PASS 仍可作为历史异常的关闭选项；原生关闭入口重新核谱系与证据。历史 UNVERIFIED 原样保留。存在未处置异常时，即使最终集成已有 PASS，也拒绝 `complete_requirement`。

只读工作输入、进度、周期报告与待决目录显示异常状态、后续 owner 及等待链。修复派单沿已有 outbox 契约投递；没有从维护会话直接发群消息。

## 回归与现场验证

- 隔离 Git、SQLite、真实 worker 和受控 runner 覆盖：证据保留、原 owner 安全释放、worker 退出不等于业务完成、已完成任务重新派单且幂等、授权撤销/越界原子拒绝、旧结果恢复、错误 PASS 不得关闭异常、机制阻断、实际修复→独立验证→合入→补验→显式关闭、调查到期唤醒。
- 语义工具回归覆盖稳定 ID、阻断保留、完整工件、来源变化、记忆过期、工具发现、真实 ACK 一致性、查询只读性、短错误和幂等日志。
- 首次扩大回归发现测试解释器缺少 pytest；隔离测试环境补齐依赖后重跑，不修改常驻 Hermes 的生产依赖，不将此类环境缺口伪装为业务 FAIL。
- 最终 212 项合并回归全部通过（192.626 秒），另已完成 compileall、diff --check、新模块全部函数的热加载清单核对、文档本地链接及 SVG XML 检查。此前一轮 211 项通过后增加了跨任务源 writer 检查并再次完整验证。
