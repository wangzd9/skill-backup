统计口径必须先明确。

- 主来源为 `/home/wang/.hermes/runtime/role-usage.db`，按请求 started_at 归窗，使用物理请求身份，不叠加 sessions 累计值。3,470次物理请求中3,466次已有完整prompt/output用量，4次在采样时尚无用量，不按0计算。
- 本文“输入”指已记录的prompt_tokens，包含可能被缓存复用的上下文；不是非缓存计费输入。规范化的input_tokens拆分字段全部未知，不能自行用0补齐。见[用量规范化](/home/wang/work/hermes-role-runtime/usage_accounting.py:143)。
- reasoning_tokens与cache_write_tokens未取得有效覆盖；不能断言没有推理或缓存写入。输出也不能未经依据再叠加一次reasoning。
- 缓存读取是输入的一部分，不能加到prompt总量上重复计数。本地模型缓存缺字段不等于没有缓存。
- 另外核对了可从服务诊断定位的OCR会话，按response时间归窗并对复用session去重。它不保证覆盖全部在途/未诊断OCR、独立强审或其他工具调用，故不声称拿到了整套系统所有模型用量。
- 字节、字符、文件读取次数及SQLite大小用于定位结构，不换算成实测token。历史账本存了3GB结果，也不意味着这些内容全部进入了模型请求。

具体优化机会如下。

1. **优先把协调者输入改成当前决策所需的状态与增量。**

   227份可解析协调者启动包中，初始消息大小中位数225,988 bytes。最近一份业务packet为186,065 bytes，主要组成如下。

   | 字段 | bytes | 数量 |
   |---|---:|---:|
   | events | 56,206 | 33个投影事件 |
   | external_actions | 33,833 | 42条 |
   | verifications | 24,108 | 60条 |
   | candidates | 22,743 | 31条 |
   | completion | 12,299 | 6个字段 |
   | verification_retirements | 7,479 | 3条 |

   最后十份启动包中，events只有两种内容哈希，plans完全相同，candidates只有三种。大量历史内容会跨会话重新进入输入，随后还随工具交互多次重发。最近五份已记录协调者会话首个请求的输入均约121K；连续接续仍未推进processed=9549。

   [current_input](/home/wang/work/hermes-role-runtime/workflow_runtime.py:473)按run装入候选、验证、动作和最终验收资料；已有[历史/长正文投影](/home/wang/work/hermes-role-runtime/workflow_views.py:47)，但未将当前动作的必需事实与终态历史充分分开。[requires_paging](/home/wang/work/hermes-role-runtime/workflow_runtime.py:528)超过32KiB只设置提示，不是启动包硬预算。

   建议按“本次动作”组织输入：当前身份/版本、下一步、相关对象、完整未闭合门禁与必要证据。终态历史用保真索引及内容哈希引用，字段在同一包内去重。所有未关闭FAIL、UNKNOWN、有效授权边界及当前判断所需证据必须可见；未展开的原始证据继续可检索，模型不能据引用宣称已经阅读。执行门仍复核权威原始状态，不能靠薄视图直接放行。

   接续需要启动快照加已处理水位之后的增量，不能把先前上下文在新会话中不存在的问题交给模型凭空记忆。工作单checkpoint应携带已核实事实、文件/接口版本和下一处定位；变化即失效重读。

2. **减少没有新工作可处理的模型启动，并修复重复分页。**

   上一轮已确认checkpoint控制字段误置导致有效游标不推进。本轮消息样本中，协调者role_work_input共有472次，其中145次直接得到PAGE_AFTER_NOT_PREVIOUSLY_ISSUED拒绝；TESTER还有24次。它们是工具回包中的明确拒绝，不是把历史日志命中数当事故数。

   227个协调者业务会话按已提交动作分组：108个只提交checkpoint，88个未提交协调命令；两组累计输入约191.3M。另一个会话只提交checkpoint/safe_release。这个群体值得优先核对，但阅读、归纳和交接也可能有价值，不能宣称191.3M全部浪费，提交命令也不等于命令已经提交成功。

   建议先修正确ACK、有效水位回执及安全续读契约；随后以相关业务变化、可执行动作和有界复核时点决定是否启动模型。同一问题、同一状态、同一版本没有变化时，程序记录等待和退避。新候选、审查结果、控制动作或必要超时仍应及时唤醒，不能靠统一拉长轮询来省token而拖慢开发。

   每次省掉的工具纠错往返，通常不只是省一条短错误文字，还能省下一轮大上下文重发。需要按真实请求关联衡量，不能把工具次数与API次数一对一相加。

3. **让工具发现结果与角色能力一致，减少确定会被拒绝的调用。**

   最近24小时协调者terminal有148个工具回包，全部包含明确error，仅两种正文，146次完全重复；TESTER terminal有64次，全部为error。协调者write_file、tool_call和execute_code的样本也有持续拒绝。

   [角色用法](/home/wang/work/hermes-role-runtime/workflow_tool_bridge.py:34)已经说明协调者禁用普通terminal等动作，但[业务会话工具集](/home/wang/work/hermes-role-runtime/workflow_runtime.py:182)仍统一列出terminal/file/skills及角色工具，模型仍有机会反复选到不可用能力。

   建议按角色提供稳定且精简的可用工具定义，对只读查询、受控命令和专用测试入口给出明确映射。权限检查继续作为底层保护；省token的方式是减少无效选择，不是开放原本禁止的工具。完整schema披露、嵌套payload及测试参数应在调用前明确；同类确定拒绝后返回可直接采用的合法下一步，避免重新探索一整套工具。

   TESTER role_test_command的136个回包中34个含明确error，部分涉及payload、pytest格式和command_id冲突。提前预检、区分未启动与已启动状态，可以减少纠错轮次，同时保留测试固定版本、真实结果与幂等门禁。

4. **把多次窄搜索和重复阅读合并成有边界的信息获取。**

   协调者search_files有1,132次回包，其中766次与同角色其他回包完全一致；C的read_file为393次，其中144次正文完全重复。C对同一bag_cleanup_service.py路径读取54次，但这些读取可能属于不同片段或不同版本，不能把54次全部当重复全文。

   建议在同一次工具请求中批量查询相互独立的问题，返回定位、相关函数和有界片段；每次判断结束保存路径、范围、版本哈希和结论。对于未变化内容，可沿用保真的已核实事实，再按需展开；代码、接口、AC或环境变更后重新读取。独立测试者仍自行验证，不能把开发者的“已确认”当成独立证明。

   输出大的完整工具日志写为可核验artifact，模型先获得退出码、失败项、相关片段及定位。需要裁决时读取原文；不能只保留一句“全部通过”。同时避免工具回包过小而迫使模型连续几十次翻页，目标是降低完成同一判断的总往返次数。

5. **优化稳定前缀与缓存，但先补本地缓存观测。**

   最近24小时cache_read有值的请求只有8次，占3,470次的0.23%，全部属于云端。仅这8次可比较记录的输入为706,594、缓存读为483,328，比例68.4%；不能把该比例推广至全部请求。本地3443次有输入记录，但缓存字段覆盖为0，真实命中情况未知。

   建议保持角色规则和工具schema的稳定版本及顺序，稳定合同放前部，时间、水位和最新变化放后部；补采实际提供方的命中/未命中字段或服务端可归属指标，再评估跨回合、跨会话的前缀复用。API返回的prompt计数可能包含缓存读，缓存命中提高不一定降低逻辑输入token，却可能降低prefill资源或费用。

   本次没有采集请求组装层每个部分的真实分词结果，无法精确拆出规则、skill、schema、业务packet和历史各占多少。下一步应在组装层仅记录这些部分的token/字节大小与哈希；不需要记录提示正文。

6. **先缩输入，再评估交接和压缩策略。**

   [当前默认会话策略](/home/wang/work/hermes-role-runtime/workflow_sessions.py:8)为48次请求提示交接、64次请求上限，以及128K近似输入阈值。有效配置未覆盖这些默认值。

   最近五份协调者预算文件checkpoint_required均为false，近似输入约88K～105K。因此当前证据不支持“近期会话反复接续都是阈值强制轮换”的结论；近似计数与提供方实际计数也不应混为一谈。见[预算样本](/home/wang/work/doc/analysis/coordinator-health-audit-20261030/token-audit/session-budget-samples.json)。

   不建议直接提高上限来容纳更多旧上下文。应先减启动包及重复读取，再按实际分词和安全交接耗时校准阈值。压缩需要保存当前合同、未闭合问题、证据引用和具体进展；其成本应与后续多轮重发节省一起计算，不能因压缩本身调用模型就直接取消。

可量化的收益应采用敏感性测算，而不是把某个疑似浪费群体全部删除。

| 假设，按最近24小时已知用量测算 | 理论少发输入 | 占当前输入 |
|---|---:|---:|
| 协调者每个有用量请求平均减少20K输入，调用数不变 | 40.38M | 10.0% |
| 协调者每个有用量请求平均减少30K输入，调用数不变 | 60.57M | 15.1% |
| 全部有用量请求平均减少20K输入，调用数不变 | 69.32M | 17.2% |
| 确认并消除100次冗余协调请求，按当前平均量估算 | 约12.56M | 约3.1% |

这些数字是条件成立时的算术结果，不是已经证明能去掉的内容或已经实现的收益。缩输入与减调用存在重叠，不能直接把比例相加；缓存收益也不能再与逻辑token减少重复计算。是否保持效果和效率，需要在实施后验证。

建议先以“同类任务的输入量减少10%～20%，交付质量和耗时无退化”为一阶段验证目标。当前证据支持优先尝试这个量级，尚不足以承诺必达，更不足以承诺减半。主要实施顺序为：有效游标与重复唤醒 → 协调者决策包 → 角色工具可发现性/完整预检 → 批量查询及版本化阅读 → 缓存观测与前缀复用。

每一批都应对照同类工作阶段的基线，而非仅比较两个任务难度不同的自然日。至少观察：输入/输出/缓存覆盖、完成同一判断的API轮数、首次验收结果、最终集成新增缺陷、未闭合FAIL/UNKNOWN保留率、用户重复介入次数，以及接纳至交付耗时和事件至处理延迟。成本按同类已验收交付及其返修全过程累计，不能只看单次请求变短而忽略调用变多、漏验或后续返工。测试范围、独立性、审查义务、固定SHA、证据核验、写者互斥和副作用幂等必须保持；模型档位和推理预算不是本轮首要削减对象。

“质量不变”不能由少发了多少字符来证明。应先实施能够机械核对的保真去重与正确事件接续，再通过真实任务的质量、延迟和成本指标判断收益是否成立。
